## P19：上线你的产品并跑完第一个增长循环

这是全课程的最后一个项目，也是唯一一个**成败不由你单独决定**的项目 —— 前面所有项目只要你把活干完就算成功，这个项目需要真实的陌生人参与。

所以验收标准也不同：**不看用户数，看你能不能用数据说清"下一步该改什么"**。有 30 个用户但你知道他们卡在哪、为什么不付费、下一步改什么，比有 300 个用户但说不清任何原因要好得多。

### 项目目标

把 P17/P18 的产品真正推出去，完成一次完整循环：

```
发布 → 获客 → 埋点观测 → 找出瓶颈 → 改一处 → 再看数据
```

具体包含：

- 用 L19-01 的方法完成一轮一对一冷启动
- 用 L19-02 的意图分析规划第一批内容
- 用 L19-03 的埋点搭起漏斗与队列分析
- 用 L19-04 建立支持流程与反馈到待办的转化
- 用 L19-05 搭一个运营 Agent 看板
- 用 L19-06 写下你的评估点与节奏规划

时间跨度建议 **4 周**。这个项目和前面不同 —— 它需要真实时间流逝才有数据。

### 验收标准

- [ ] 产品公开可访问，陌生人无需你协助能完成主流程
- [ ] 发布材料：一篇符合叙事结构的发布帖（有独立于产品的观察）
- [ ] 一对一记录：≥30 次个性化接触，含原话记录
- [ ] 埋点上线：七个关键事件 + 来源标记参数 + 事件名白名单
- [ ] 漏斗数据：访问/注册/激活/付费四层的真实数字
- [ ] 队列表：至少两周的留存数据
- [ ] `first_run` 有明确定义，且是"得到价值"而非"点了按钮"
- [ ] 支持流程：响应预期已公示 + 结构化条目记录（记原话、记次数、分四类）
- [ ] 流失回访：给 7 天未回访用户发过手写风格邮件，有回复记录
- [ ] 反馈到待办的转化记录：至少 3 条从对话变成的产品改动
- [ ] 运营 Agent：日报自动发送，数据库用只读角色（系统层验证）
- [ ] 迭代计划：基于数据说清下一步改什么，以及为什么
- [ ] 个人评估点：日期 + 指标 + 达不到时的动作

### 分阶段实施

**第 0 周：准备（约 1.5 小时）**

上线前把观测装好。**先埋点再推广**，否则第一波流量的数据全部浪费 —— 而那波数据是最宝贵的（它告诉你陌生人第一次看到你的产品是什么反应）。

清单：

```
- [ ] events 表 + 七个事件 + 白名单 assert
- [ ] first_run 定义写下来（一句话，可验证）
- [ ] 来源标记参数格式确定
- [ ] 每周报表脚本（先手工跑也行）
- [ ] 支持邮箱 + 响应预期页面
- [ ] 隐私政策与服务条款（P18 的产出）
```

`first_run` 的定义要经得起这个检验：**如果一个用户只做到这一步就走了，他有没有从你的产品得到东西？** 答"没有"，说明定义太靠前。

**第 1 周：一对一冷启动（约 1.5 小时 + 每天半小时）**

按 L19-01 的流程做。目标是 30 次接触、20 次真实对话、10 个人真的用了。

每次对话后立刻记原话。建议用一个简单的表：

```markdown
| 日期 | 渠道 | 是否回复 | 是否试用 | 原话摘录 | 卡在哪 |
```

「卡在哪」这一列到周末会成为你最重要的产出。

这一周不要加功能。忍住。

**第 2 周：修卡点 + 发布（约 1.5 小时）**

先看第 1 周的「卡在哪」，统计出现次数，**只修出现 3 次以上的**。

然后写发布帖，按 L19-01 的叙事结构：具体问题 → 反直觉的事实 → 只解决这一点的东西 → 具体效果 → 明确限制条件的链接。

分散发到 3-5 个社区，不要同一天全发 —— 每发一次根据反应调整表述，后面几次的效果通常明显好于第一次。

**第 3 周：数据分析（约 1 小时）**

现在有数据了。回答这四个问题：

```
1. 四层漏斗各是多少？哪一层掉得最狠？
2. 按来源分组，哪个渠道的用户真的完成了核心动作？
3. 第一周注册的人，第二周回来了多少？
4. 撞到额度上限的人有几个？他们付费了吗？
```

第 2 问经常给出意外答案 —— 带来最多访问的渠道往往不是带来最多激活用户的渠道。找到这个差异，你就知道下一轮该在哪投入。

第 4 问是判断定价问题的关键（L19-03 讲过）：撞额度的人少 → 免费额度给多了；撞了但不付费 → 价值表述有问题。

**第 4 周：运营 Agent + 迭代计划（约 1.5 小时）**

搭 L19-05 的日报 Agent。最小版本：只读数据库角色 + 拉三类数据 + 模型写 150 字简报 + 邮件发给自己。带上那三条 prompt 约束。

然后写迭代计划。格式：

```markdown
# 下一阶段迭代计划
## 数据现状
访问 ___ → 注册 ___(__%) → 激活 ___(__%) → 付费 ___(__%)
次周回访 __%  ｜ 撞额度 __ 人，其中付费 __ 人

## 最大的瓶颈
（只写一个。写两个说明你还没判断出来）

## 判断依据
（哪个数字告诉你的，以及为什么排除了其他可能）

## 下一步要改的一件事
（具体到能开始做）

## 怎么验证有没有效
（改完之后看哪个数字，多久之后看，涨到多少算有效）
```

「只写一个瓶颈」是硬要求。一人公司同时修三件事的结果是三件都没修好，而且改动混在一起你无法判断哪个起了作用。

### 常见翻车点

**先推广后埋点。** 第一波流量的数据永远拿不回来了 —— 而那波恰恰是最纯粹的（没有你的干预、没有你的解释）。

**`first_run` 定义太靠前。** 定义成「点了开始按钮」，激活率 80%，看着很好，但毫无意义，还会让你误判瓶颈位置。

**拿 20 个用户的数据做统计推断。** 样本这么小，转化率的波动全是噪音。这个阶段**用户访谈的信息量远大于统计数字** —— 一个人告诉你「我以为要付费才能试」，比任何漏斗图都有用。

**一次改五件事。** 数据变了，你不知道是哪一件起的作用，下次也就无法复用这个经验。

**只统计不去问。** 数据告诉你「70% 的人在注册后离开了」，但只有对话能告诉你为什么。这两者必须配合，缺一个都得不出结论。

**被虚荣指标带偏。** 某个渠道给你带来一万次访问、零个激活，然后你继续投入那个渠道。这是人群不匹配的信号，不是需要努力的信号。

**跳过流失回访。** 来找你的用户是最好的那批，真正的问题在默默走掉的人身上。那封邮件回复率只有 5%-15%，但每条回复的价值极高。

### 交付形式

```
docs/
  launch-post.md        # 发布帖（含叙事结构）
  outreach-log.md       # 一对一接触记录（含原话）
  analytics-report.md   # 漏斗 + 队列 + 分渠道分析
  feedback-to-todo.md   # 反馈转化记录（≥3 条）
  next-iteration.md     # 迭代计划
  personal-plan.md      # 评估点与节奏规划
src/
  analytics/events.py   # 埋点（含白名单 assert）
  ops/daily_brief.py    # 运营 Agent 日报
scripts/
  weekly_report.py      # 每周报表
  churn_email.py        # 流失回访
```

### 自检问题

交付前问自己：

- 我的漏斗哪一层掉得最狠？我知道原因吗？（"不知道"是合理答案，但接下来要有一个去问清楚的动作）
- 哪个渠道带来了完成核心动作的用户？和带来最多访问的是同一个吗？
- 我能说出最近三个用户分别是谁、遇到了什么问题吗？
- 我的运营 Agent 有没有可能改到数据？（应该是"物理上做不到"）
- 我的评估点写下来了吗？在一个三个月后我一定会看到的地方吗？
- 如果收入永远不来，这件事我还愿意做吗？

最后一个问题不是修辞。认真回答它，然后据此安排接下来六个月。

### 要点总结

- 这是唯一**成败不由你单独决定**的项目；验收标准是**能不能用数据说清下一步改什么**，不是用户数。
- **先埋点再推广**：第一波流量的数据最宝贵也最拿不回来。
- `first_run` 的检验标准：**只做到这一步就走的用户，有没有得到东西？** 定义太靠前会让激活率好看但误导判断。
- 冷启动第一周**不要加功能**；第二周只修**出现 3 次以上**的卡点。
- 发布帖分散发到 3-5 个社区，**每次根据反应调整表述**，后几次效果通常明显更好。
- 数据分析必答四问，其中「**哪个渠道带来了激活用户**」常给出意外答案，「**撞额度的人付费了吗**」是判断定价问题的关键。
- 迭代计划**只写一个瓶颈**：同时修三件事的结果是三件都没修好，且无法归因。
- 样本小的阶段，**访谈的信息量远大于统计数字**；只统计不去问，永远得不出原因。
- 运营 Agent 的只读权限要**物理上做不到写**，不是靠 prompt 约束。
