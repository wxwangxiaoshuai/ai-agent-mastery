## Agent 健壮性全景：为什么"能跑"≠"可靠"

M5 的 ReAct Agent（L05-02 起）和 M6 的工具箱 Agent 都能"跑通"——在正常条件下完成任务的 demo。但生产环境不是 demo：API 会限流、网络会断、模型会幻觉、工具会超时。**"能跑"和"可靠"之间，隔着一整套 Harness 工程。**

先用监控面板感受「重试 → 熔断 → 降级」在故障注入下如何联动，再进入故障分类与可靠性指标。

::interactive{type="harnessMonitor"}

### Demo vs 生产：故障无处不在

```
Demo 环境（你演示时）：
  用户提问 → LLM 推理 → 工具调用 → 返回答案 ✓

生产环境（真实用户使用时）：
  用户提问 → LLM 推理 → 工具调用 → 429 限流！
  用户提问 → LLM 推理 → 工具调用 → 超时（外部 API 慢）
  用户提问 → LLM 推理 → 幻觉工具名 → 调用失败
  用户提问 → LLM 推理 → 推理发散 → 步数耗尽
  用户提问 → 网络 503 → 完全无响应
```

### Agent 故障模式分类

| 类别 | 故障示例 | 频率 | 影响 |
|------|----------|------|------|
| **模型故障** | API 429 限流、503 服务不可用、模型幻觉 | 高 | Agent 无法推理或推理错误 |
| **工具故障** | 外部 API 超时、返回格式异常、权限不足 | 中高 | Agent 无法获取信息 |
| **网络故障** | DNS 解析失败、连接超时、TLS 错误 | 中 | 请求发不出去 |
| **逻辑故障** | 死循环、步数耗尽、上下文超限 | 低 | Agent 卡住或产出错误 |

**关键认知**：模型故障和工具故障是最高频的——它们不是"意外"，而是**常态**。你的 Agent 必须假设它们会发生，并提前准备好应对策略。

### 可靠性指标：MTBF 和 MTTR

```
MTBF (Mean Time Between Failures) = 两次故障之间的平均时间
MTTR (Mean Time To Recovery)      = 故障后的平均恢复时间

可用性 = MTBF / (MTBF + MTTR)

示例（简化：忽略修复占用时间，按日历时间粗算）：
  Agent 每天故障 3 次，每次 2 分钟恢复
  MTBF ≈ 24h / 3 = 8 小时 = 480 分钟
  MTTR = 2 分钟
  可用性 = 480 / 482 = 99.6%
```

**Agent 的 MTTR 是关键**——你无法阻止故障发生，但可以缩短恢复时间。Harness 工程的目标就是把 MTTR 从分钟级降到秒级。

### Harness 工程：给 Agent 穿上"盔甲"

Harness 不是 Agent 的功能逻辑，而是**包裹在 Agent 外面的保护和恢复机制**：

```
┌─────────────────────────────────────────────┐
│              Harness 层（本模块）              │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐       │
│  │ 重试  │ │ 超时  │ │ 熔断  │ │ 降级  │       │
│  └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘       │
│     └────────┴────────┴────────┘             │
│              ┌─────────────┐                 │
│              │ Agent Loop  │  ← M5/M6 的 Agent │
│              └─────────────┘                 │
│              ┌─────────────┐                 │
│              │ Checkpoint  │  ← 状态持久化     │
│              └─────────────┘                 │
└─────────────────────────────────────────────┘
```

| Harness 组件 | 作用 | 对应课程 |
|-------------|------|----------|
| 重试 + 退避 | 暂时性故障自动恢复 | L07-02 |
| 超时控制 | 防止永久挂起 | L07-02 |
| Checkpointing | 失败后从断点恢复 | L07-03 |
| Circuit Breaker | 防止级联故障 | L07-04 |
| 限流 + 队列 | 峰值保护 | L07-04 |
| 降级链 | 故障时切换到备用方案 | L07-05 |

### Agent 失效的三种"看起来还在工作"

传统服务挂了会报错，Agent 的可怕之处在于它经常**不报错地失败**。
这三种形态在监控里都表现为"请求成功、状态码 200"：

**一、静默截断。** 上下文超了预算，最早的几轮对话被悄悄丢掉。
Agent 不会告诉你它忘了什么，它只会开始给出前后矛盾的回答。
这类问题在测试环境几乎测不出来——测试对话都很短。

**二、原地打转。** ReAct 循环里，模型反复调用同一个工具、拿到同样的失败结果、
再原样重试。每一轮都"成功"，直到撞上步数上限或者烧完你的预算。
根因通常是工具返回了一个不可执行的错误信息（L06-02 讲过这件事）。

**三、自信地跑偏。** 模型误解了任务，然后一路把错误的理解贯彻到底，
最终交出一份格式完美、内容全错的结果。这类失败在人工抽检之前完全隐形。

```
传统服务的故障：  请求 → 500 → 告警 → 有人被叫醒
Agent 的故障：    请求 → 200 → 无人察觉 → 三周后用户投诉
```

**工程启示**：Agent 的可观测性不能只盯"成功率"。至少还要盯这几个信号——
每次任务的**循环轮数分布**（长尾意味着在打转）、
**上下文被裁剪的次数**（意味着在遗忘）、
**同一工具连续调用的次数**（意味着在重试无效动作）。
M13 讲全链路 trace 时会把这些指标落地。

### 一个反面例子：从 Demo 到事故

下面这段代码在演示里跑得很好，在生产里会以三种方式伤害你：

```python
# 反面教材：一个"能跑"的 Agent 循环
def run_agent(question: str) -> str:
    messages = [{"role": "user", "content": question}]
    while True:                                    # 问题一：没有步数上限
        resp = client.chat.completions.create(     # 问题二：没有超时、没有重试
            model="gpt-4o", messages=messages, tools=TOOLS,
        )
        msg = resp.choices[0].message
        if not msg.tool_calls:
            return msg.content
        messages.append(msg)
        for call in msg.tool_calls:                # 问题三：工具异常直接冒泡
            result = dispatch(call)                #        整个任务当场失败
            messages.append({"role": "tool", "content": result,
                             "tool_call_id": call.id})
```

三处问题分别对应后面三节课：

| 问题 | 后果 | 对应课程 |
|------|------|---------|
| `while True` 无上限 | 模型打转时无限烧钱，一次事故就能烧掉整月预算 | L07-02 循环控制 |
| 无超时无重试 | 上游一次 429 就让整个任务失败；无超时则线程被永久占住 | L07-02 重试退避 |
| 工具异常直接冒泡 | 一个工具挂掉 = 整个任务失败，而它本可以被降级或跳过 | L07-03 容错与降级 |
| 状态只存在内存里 | 进程重启则全部丢失，长任务永远做不完 | L07-04 Checkpoint |

**这一节不解决它们**——只是希望你在往下学之前，先真切地看见"能跑"和"可靠"之间
差了多少东西。每加一项，代码都会变长、变啰嗦，这就是可靠性的价格。

### "能跑"→"可靠"的检查清单

在把 Agent 推向生产前，逐项检查：

- [ ] API 调用有超时设置（不是无限等待）
- [ ] 暂时性错误（429/5xx）有自动重试
- [ ] 重试有退避策略（不是立即重试）
- [ ] 有最大重试次数（不是无限重试）
- [ ] 工具调用有独立超时（不跟着 LLM 超时走）
- [ ] Agent Loop 有步数上限
- [ ] 长任务有 Checkpoint（失败不从头开始）
- [ ] 外部服务故障不会导致 Agent 永久卡住
- [ ] 有降级方案（主模型不可用时切备用）
- [ ] 有日志记录（出问题能排查）

> 如果以上任何一项没做，你的 Agent 就还停留在"能跑"阶段，不适合生产环境。

### 要点总结

- "能跑"的 Agent 和"可靠"的 Agent 之间隔着一整套 Harness 工程
- 四类故障模式：模型故障（最高频）、工具故障、网络故障、逻辑故障
- 可靠性 = MTBF / (MTBF + MTTR)——Harness 的目标是缩短 MTTR
- Harness 六组件：重试退避、超时控制、Checkpoint、Circuit Breaker、限流队列、降级链
- Agent 最危险的失败是"不报错的失败"：静默截断、原地打转、自信跑偏
- 只盯成功率会漏掉全部三种；还要盯循环轮数分布、上下文裁剪次数、同工具连续调用次数
- 一个没有步数上限、没有超时重试、工具异常直接冒泡的循环，是最典型的 Demo 级代码
