## Agent 设计模式全景

M5 带你从零实现了 ReAct、学了 Plan-Execute、了解了 Reflection。这三个模式不是孤立的——它们属于一个更大的"Agent 设计模式分类体系"。这一节的目标是：**给你一张全景地图，让你知道所有模式长什么样、各在什么位置、以及怎么选。**

### 为什么需要设计模式

Agent 开发不是每次都从零发明架构。就像 GoF 设计模式之于面向对象编程，Agent 设计模式是从大量工程实践中提炼出来的**经过验证的、可复用的架构模板**。

学完 M5-M11 后，你脑子里会有一堆技术点：ReAct、Plan-Execute、Supervisor、Debate、HITL……如果没有一个统一的分类框架来组织它们，就会出现三个问题：
- 不知道"我该用哪个模式"——决策靠直觉
- 不知道"这些模式之间是什么关系"——看不出层级和组合
- 不知道"还有哪些模式我没学过"——知识盲区不自知

Anthropic 在 2024 年 12 月的 _Building effective agents_ 一文中将 Agent 设计模式归纳为 5 类基础模式。这是业界最权威的分类框架之一，也是本节的主线。

### 五大基础模式

#### 1. Prompt Chaining：链式串联

```
[输入] → [LLM A] → [输出A] → [LLM B] → [输出B] → [LLM C] → [最终输出]
```

**核心思想**：A 的输出是 B 的输入，按固定步骤串联多个 LLM 调用。每一步有明确的输入输出契约。

**适用场景**：任务可拆成固定的、有先后依赖的子任务。

**典型示例**：
- 写文档 → 翻译 → 格式化
- 数据清洗 → 统计分析 → 生成报告
- 需求分析 → 生成大纲 → 逐节撰写

**关键判断**：步骤是否**预先确定**？如果是，Prompt Chaining 是最简单可靠的选择。

**在课程中的位置**：M2 Prompt 工程——这是最基础的模式，本质是"把多个 Prompt 串起来"。

#### 2. Routing：按意图分发

```
                     ┌→ [Handler A: 退换货]
[用户输入] → [分类器] ─┼→ [Handler B: 技术咨询]
                     └→ [Handler C: 投诉]
```

**核心思想**：分类输入意图 → 分发到专门的处理者。每个处理者只处理自己擅长的那类问题。

**适用场景**：输入类型差异大，各自需要不同的处理方式。

**典型示例**：
- 客服系统：问题分类 → 退换货 / 技术咨询 / 投诉 → 不同 handler
- 代码助手：用户意图分类 → 写代码 / 解释代码 / 改 bug / 写文档
- 内容平台：上传内容分类 → 文章 / 视频 / 图片 → 不同处理管道

**关键判断**：输入是否**类型差异大**且各自需要不同的处理逻辑？

**在课程中的位置**：M6 工具使用——Function Calling 做意图分类 + 路由到不同工具。

#### 3. Parallelization：并行执行

```
          ┌→ [子任务 A] ─┐
[输入] → ─┼→ [子任务 B] ─┼→ [聚合] → [输出]
          └→ [子任务 C] ─┘
```

**核心思想**：同时执行多个独立子任务，然后聚合结果。

**两种子类型**：
- **Sectioning**：把大任务切成独立小块，并行处理。例如：长文档分块 → 并行摘要 → 合并。
- **Voting**：同一任务发给多个模型/视角，投票选出最佳。例如：多路审核 → 投票决策。

**适用场景**：子任务之间没有依赖，可以同时执行。

**典型示例**：
- 同时搜索多个数据源 → 合并去重
- 代码安全检查：并行跑 lint / type-check / 安全扫描 / 依赖检查
- 多路翻译 → 投票选最佳

**关键判断**：子任务是否**真的独立**？如果有依赖，用 Orchestrator-Workers。

**在课程中的位置**：M6 并行工具调用 + M11 多 Agent 并行协作。

#### 4. Orchestrator-Workers：动态编排

```
[Orchestrator] → 分析任务 → 拆分子任务
       ↓
  ┌→ [Worker A] → 结果A
  │→ [Worker B] → 结果B
  │→ [Worker C] → 结果C
       ↓
[Orchestrator] → 综合结果 → 判断是否需要更多子任务
```

**核心思想**：中央规划者（Orchestrator）动态拆任务 → 派发给多个 worker → worker 返回结果 → 规划者判断是否需要继续。

**与 Prompt Chaining 的区别**：Chaining 的步骤是**预先确定的**，Orchestrator-Workers 的步骤是**运行时动态规划的**。

**适用场景**：子任务无法预知，需要动态规划，且各子任务可能相互依赖。

**典型示例**：
- 深度研究 Agent：读问题 → 规划搜索方向 → 派搜索 → 读结果 → 决定是否需要补搜 → 派总结 → 综合
- 代码重构：分析代码库 → 规划重构步骤 → 派子任务 → 检查结果 → 决定是否继续

**在课程中的位置**：M11 Supervisor 模式 / CrewAI。

#### 5. Evaluator-Optimizer：迭代优化

```
[Generator] → 产出 → [Evaluator] → 评分/反馈
    ↑                                    ↓
    └────── 修改 ←────── 未达标 ←─────────┘
                          ↓
                      达标 → 最终输出
```

**核心思想**：生成者产出 → 评估者打分 → 反馈 → 生成者改进 → 循环迭代，直到达标。

**与 Reflection 的区别**：Reflection 是**自我**批评（同一个模型评判自己的输出），Evaluator-Optimizer 是**外部**评估者评判生成者的输出。外部评估者可以有不同的评判标准和更严格的检查清单。

**适用场景**：有明确的质量标准，且一次生成难以达到理想效果。

**典型示例**：
- 代码生成 → review → 修改 → 再 review（L17-14 的 Gate 4 就是这个模式）
- 文章草稿 → 打分 → 修订 → 再打分
- 翻译 → 质量评估 → 修正 → 再评估

**在课程中的位置**：M5 Reflection + M13 评估体系。

### 模式选择决策树

用下面这个决策树来为你的任务选模式。核心问题只有四个：

```
任务步骤是否线性且固定？
  ├─ 是 → Prompt Chaining
  └─ 否 → 输入类型差异大，需要不同处理方式？
           ├─ 是 → Routing
           └─ 否 → 子任务可以并行执行（无依赖）？
                    ├─ 是 → Parallelization
                    └─ 否 → 子任务不可预知，需要动态规划？
                             ├─ 是 → Orchestrator-Workers
                             └─ 否 → 有明确的客观质量标准？
                                      ├─ 是 → Evaluator-Optimizer
                                      └─ 否 → 单次 LLM 调用（多数情况兜底）
```

### 模式与课程模块的映射

| 模式 | 先修课程模块 | 深入学习 |
|------|------------|---------|
| Prompt Chaining | M2 Prompt 工程 | 链式 Prompt 设计 |
| Routing | M6 工具使用 | Function Calling 做意图分类 |
| Parallelization | M6 并行工具调用 | M11 多 Agent 并行 |
| Orchestrator-Workers | M11 Supervisor / CrewAI | 动态任务编排 |
| Evaluator-Optimizer | M5 Reflection + M13 评估 | 自动化评测流水线 |

### 模式可以组合

一个真实的 Agent 系统通常不是单一模式，而是多个模式的组合。例如：

- **深度研究 Agent**：Routing（分类问题类型）+ Orchestrator-Workers（动态搜索）+ Evaluator-Optimizer（质量审查）
- **代码审查 Agent**：Parallelization（并行检查）+ Evaluator-Optimizer（迭代修复）
- **客服 Agent**：Routing（分发意图）+ Prompt Chaining（收集信息→查询→回复）

**组合原则**：从最外层开始选模式（这个系统的整体流程像什么），然后向内层递归（每个子任务用什么模式）。

### 动手 5 分钟

1. 打开 `patternSelector` 交互组件，针对你最近做过的或打算做的 3 个任务，分别点选「是/否」走完决策树，记下推荐模式。
2. 对每个推荐结果，问自己：这个推荐合理吗？如果按推荐模式设计，我的系统架构会是什么样？
3. 挑一个任务，用选定的模式画出它的数据流草图（纸上画就行，不用写代码）。

**验收标准**：能用自己的话说出五大模式各自的核心区别，以及它们在你课程学习路径上的位置。如果你发现自己总是选同一个模式，说明你可能在用它解决不适合的问题——回到决策树，重新走一遍。

### 要点总结

- **Agent 设计模式 = 经过验证的、可复用的架构模板**。GoF 模式之于 OOP，Agent 设计模式之于 AI Agent。
- 五大基础模式按 Anthropic 分类：**Prompt Chaining**（链式串联）、**Routing**（按意图分发）、**Parallelization**（并行执行）、**Orchestrator-Workers**（动态编排）、**Evaluator-Optimizer**（迭代优化）。
- 选择模式的核心问题只有四个：**步骤是否预定义、输入是否类型差异大、子任务是否可并行、是否需要动态规划**。
- 各模式不是孤立的——真实 Agent 系统通常是多个模式的组合，从最外层开始选，向内层递归。
- 学完 M5 后，你已经掌握了 ReAct（M5）、Plan-Execute（M5）、Reflection（M5），后续 M6 教 Routing+Parallelization，M11 教 Orchestrator-Workers+Debate，M13 教 Evaluator-Optimizer 的评估体系。
- 如果你发现自己总是选同一个模式，说明你可能在用它解决不适合的问题——回到决策树，重新走一遍。
