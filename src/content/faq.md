# 常见问题与踩坑记录

AI Agent 开发中最常见的错误和疑问，按模块分类。每个条目包含：问题现象 → 根因 → 解决方法。

## M1：LLM 基础

**Q：为什么 temperature=0 时，同样的 Prompt 两次输出还是不同？**

根因：GPU 浮点运算的并行归约顺序不确定，即使 temperature=0，两个概率接近的 token 也可能因浮点误差被翻转。加上服务端可能路由到不同硬件或无声升级模型。

解决：不要写"输出必须逐字相等"的断言。Agent 测试应断言**结构与语义**——JSON schema 是否合法、关键字段是否包含、是否调用了预期的工具。详见 L01-01 和 M13 测试策略。

**Q：为什么我的 API 调用返回空响应或截断？**

根因：`max_tokens` 参数设得太小，模型来不及输出完整内容就被截断了。

解决：检查 `max_tokens` 是否足够覆盖预期输出长度。如果确实需要限制长度，在 Prompt 中要求模型"在 N 个 token 内完成"比硬截断更可靠。

**Q：logprobs 能用来判断模型是否在"胡说"吗？**

根因：不能。模型可以对自己编造的内容非常自信，高概率不代表正确。

解决：logprobs 只适合两件事：标记需要人工复核的低置信回答（logprob < -5），以及在多候选之间做重排。真正可靠的做法是让答案**可核查**——RAG 带来源引用、工具调用带原始返回值。

## M2：Prompt 工程

**Q：Few-shot 示例越多越好吗？**

根因：不是。超过 5-6 个示例后边际收益递减，且示例之间可能产生意外干扰（模型学到你无意中植入的模式）。

解决：3-5 个高质量示例通常足够。优先覆盖边界情况（空输入、超长输入、异常输入），而不是不同表述的同一种情况。

**Q：结构化输出要求 JSON，但模型偶尔返回的不是合法 JSON？**

根因：模型在生成 JSON 时被截断，或者在 JSON 前后加了 Markdown 代码块标记。

解决：使用 Function Calling 的 `response_format: {"type": "json_object"}` 而非在 Prompt 里口头要求。如果仍需 Prompt 方式，在代码中做 `json.loads()` 前先 strip 掉 Markdown fence。

**Q：为什么我的 Prompt 在 GPT-4 上效果好，换到 Claude 上就不行了？**

根因：不同模型的指令遵循方式和敏感度不同。Claude 对 System Prompt 中的角色定义更敏感，GPT-4 对格式指令更敏感。

解决：不要假设 Prompt 可跨模型移植。每次换模型都要重新测试，重点关注边界情况和拒答率。

## M3：上下文工程

**Q：System Prompt 写得很详细，但模型似乎没认真遵守？**

根因：System Prompt 太长（超过 500 token），模型注意力被稀释，后半部分的指令被忽略。

解决：System Prompt 控制在 300-500 token 以内。把不常用的规则放到动态注入层（按需拼接），而不是全部放在静态底座里。详见 L03-01 和 L03-02。

**Q：上下文窗口有 200K，为什么我塞了 50K 内容就报错了？**

根因：API 的 `max_tokens` 参数（输出限制）和上下文窗口（输入+输出总限制）是分开的。你的输入+输出可能超过了窗口限制。

解决：用 tiktoken 或对应模型的 tokenizer 提前计算输入 token 数，确保 `input_tokens + max_tokens < context_window`。L03-03 的 Token 预算规划器可以帮你可视化。

## M4：RAG

**Q：RAG 检索到的文档和问题看起来相关，但生成的回答还是不对？**

根因：可能是"相关但不正确"——检索到的文档和问题语义相似，但内容不包含答案所需的信息。这是 RAG 最隐蔽的失败模式。

解决：增加 Reranking 步骤（用 Cohere Rerank 或 bge-reranker），在生成前做一轮精确排序。同时检查分块大小——块太小可能丢失上下文，块太大可能稀释相关性。

**Q：为什么我的向量搜索结果很乱，搜"苹果手机"能搜出"吃苹果的好处"？**

根因：Embedding 模型做的是语义相似度，不是关键词匹配。"苹果"在"苹果手机"和"吃苹果"中语义不同，但 Embedding 模型可能无法区分。

解决：混合检索（Hybrid Search）——向量检索 + BM25 关键词检索，两份结果合并去重。这是 M4 L04-03 讲的核心策略。

## M5：Agent 核心

**Q：Agent 陷入死循环，反复调用同一个工具？**

根因：工具返回的信息不够明确，模型无法判断"任务已完成"，于是继续尝试。

解决：三步齐下：(1) 在 System Prompt 中明确"何时停止"的条件；(2) 设 `max_steps` 硬上限；(3) 在工具返回中加入明确的完成信号（如"操作已完成，请生成最终回答"）。

**Q：什么时候用 Workflow，什么时候用 Agent？**

根因：大多数人高估了 Agent 的必要性。90% 的"Agent 需求"其实是固定流程的 Workflow。

解决：判断标准：任务步骤是固定的（即使步骤多）→ Workflow；步骤需要根据中间结果动态决定 → Agent。详见 L05-06。

## M6：工具调用与 MCP

**Q：工具描述写得很详细，但模型总是选错工具？**

根因：工具描述太长（超过 200 token），模型在多个工具间做选择时注意力被稀释。或者多个工具的功能描述有重叠。

解决：每个工具描述控制在 200 token 以内，用最明确的动词开头。确保每个工具的功能边界清晰、互不重叠。如果两个工具能做类似的事，合并为一个。

**Q：MCP Server 启用了但 Agent 连不上？**

根因：MCP 的 transport 配置错误（stdio 的 command 路径不对，或 SSE 的 URL 写错），或者 Agent 进程没有权限执行 MCP Server 的命令。

解决：先用 `mcp dev` 或手动启动 Server 验证它能独立运行，确认 transport 配置正确后再接入 Agent。

## M7：Harness 工程化

**Q：加了重试后，API 调用反而更慢了？**

根因：重试间隔太短，或者对不可重试错误（如 400）也做了重试，浪费了等待时间。

解决：只对可重试错误（429/5xx/超时）重试。指数退避 base 从 1s 起步，带随机抖动。`max_retries=3` 是合理默认值。

**Q：Circuit Breaker 熔断后一直不恢复？**

根因：冷却时间设得太长，或者熔断后没有设置半开状态的试探机制。

解决：冷却时间设为 30-60 秒。冷却结束后进入 half-open 状态，放行一个请求试探——成功则回 closed，失败则继续 open。

## M8：记忆系统

**Q：Agent 的"记忆"总是记不住很久之前的事？**

根因：你可能只用了工作记忆（当前对话历史），没有做长时记忆的持久化。

解决：至少需要三层：工作记忆（当前对话）、短期记忆（最近 N 轮摘要）、长期记忆（向量库 + 关键事实提取）。详见 L08-01 的记忆四层路由。

**Q：用户说"记住我过敏花生"，下次对话 Agent 还是忘了？**

根因：跨会话记忆需要持久化存储，且需要"记忆提取"这一步——在对话结束时主动提取关键信息存入长期存储。

解决：在每次对话结束时跑一个"记忆提取"步骤：让 LLM 总结本次对话中值得记住的用户信息，存入向量库或结构化存储。下次对话开始时检索相关记忆注入上下文。

## M9：代码沙箱

**Q：沙箱里执行 Python 代码，用户输入 `__import__('os').system('rm -rf /')` 怎么办？**

根因：默认的 `exec()` 或 `eval()` 没有隔离，可以访问宿主进程的全部能力。

解决：使用 Docker 容器隔离（每个执行在独立容器中），或使用 RestrictedPython / PyPy 的沙箱模式。资源限制（CPU 时间、内存上限、网络禁止）必须同时设。详见 L09-02。

## M10：框架编排

**Q：LangGraph 和 CrewAI 选哪个？**

根因：两者定位不同。LangGraph 是底层状态机框架（精细控制），CrewAI 是高层多 Agent 编排（快速上手）。

解决：需要精细控制状态流转、条件分支、checkpoint → LangGraph；需要快速搭建多 Agent 协作、角色定义清晰 → CrewAI。两者可以组合使用。

## M13：评估与测试

**Q：E2E 测试总是失败，但手动试又能工作？**

根因：E2E 测试用了精确断言（`assert result == "expected"`），但 LLM 输出天然不确定。

解决：E2E 测试用 LLM-as-Judge 或语义断言（`is_refusal()`、`contains_topic()`）。不要 `assert 精确相等`，`assert score >= 3` 即可。详见 L13-07。

**Q：LLM-as-Judge 给的分数不稳定，同一份输出两次打分差很多？**

根因：Judge 的 Prompt 不够精确，或者 temperature 设得太高。

解决：Judge 用 `temperature=0`，Prompt 中给出明确的评分锚点（"1 分 = 完全答非所问，5 分 = 完全正确且包含所有关键信息"）。如果仍然不稳定，跑 3 次取中位数。

## M17：AI Coding

**Q：AI 生成的代码总是重复造轮子，三个月后同一个函数有五个版本？**

根因：AI 不知道已有的代码库中有什么。每次对话是独立上下文，它看不到之前写的类似功能。

解决：在 `CLAUDE.md` 中维护一个"已有工具函数清单"，让 AI 在写新代码前先检查。用 OpenSpec 的 archive 让 AI 读取已实现的功能。详见 L17-09 和 L17-13。

**Q：AI 写的代码有大量 `try/except Exception: pass`？**

根因：AI 被训练为"防御性编程"，但过度防御会吞掉真实错误。

解决：在项目约定（CLAUDE.md）中明确写"禁止 `except Exception: pass` 或 `return None` 吞异常"。用 CI 的 ruff 规则（`B` 分类）自动检测。详见 L17-09。

## M18/M19：商业化

**Q：产品上线了但没人用，是不是功能不够？**

根因：不是。冷启动的最大障碍是"没有人在等你的产品"，不是功能缺失。

解决：上线后继续加功能通常是在回避冷启动。先做一对一接触（前 20 个用户必须来自私信/邮件/线下），听反馈修卡点，再考虑加功能。详见 L20-01。

**Q：免费用户很多但没人付费，怎么转？**

根因：免费用户的行为和付费用户完全不同，从免费期收集的所有信号都不能证明有人会付钱。

解决：从第一天就收费——哪怕只是象征性的 ¥1。收费验证的是"用户是否愿意为解决这个问题掏钱"，这是唯一需要验证的事。详见 L18-01 和 L18-02。
