## 自动化运营：用 Agent 经营你的 Agent 产品

这一节是全课程的回环。

前面十八章教你怎么给别人造 Agent。现在把这套能力用在自己身上：**你是一个人，但你的运营工作量是按用户数增长的**。写代码的时间被支持、监控、报表、对账一点点吃掉，最后你会变成自己产品的客服，而不是它的开发者。

Agent 正好适合填这个缺口 —— 但只有一部分缺口。

### 先划边界：什么能自动化，什么不能

判断依据不是技术难度，是**错了的代价和谁来承担**。

| 运营环节 | 能否自动化 | 理由 |
|---------|-----------|------|
| 监控告警与归因初判 | **可以（全自动）** | 错了只是多一条噪音告警 |
| 每周报表生成与异常标注 | **可以（全自动）** | 输出给你自己看，你会复核 |
| 支持邮件分类与草拟回复 | **半自动（人工发送）** | 内容对外，语气和承诺必须你把关 |
| 用户反馈归类与去重统计 | **可以（全自动）** | 输出是内部待办 |
| 内容初稿与更新提示 | **半自动** | 见 L20-02，事实必须你提供 |
| 成本异常检测与账号标记 | **可以（标记，不封禁）** | 标记安全，封禁不可逆 |
| 封禁账号 / 退款 / 改订阅 | **不可以** | 涉及钱和用户权益，必须人工 |
| 定价变更 / 对外承诺 | **不可以** | 后果不可逆 |
| 处理投诉与争议 | **不可以** | 需要判断和共情 |

一条通用规则：**Agent 可以读、可以分析、可以起草，但凡是「写到外面去」或「动到钱」的动作，都要经过你。**

这正是 M10 讲的 HITL 在自己生意上的应用 —— 而且这里的赌注比给客户做项目更高，因为出事没有人兜底。

### 运营 Agent 的最小架构

不需要复杂的多智能体系统。一个定时触发的单 Agent，配几个只读工具，加一个审批出口，就能覆盖大部分场景。

```
定时触发（每天 8:00）
    ↓
运营 Agent
    ├─ 只读工具：查数据库（指标）、查日志、查成本、查支付网关
    ├─ 分析：对比历史、找异常、归因
    └─ 输出：
        ├─ 自动发送：日报邮件给你自己
        ├─ 待审批队列：支持回复草稿、账号标记建议
        └─ 立即告警：故障、成本异常（推送到手机）
```

工具权限的设计原则：**给它只读账号，物理上做不到写操作**。

```python
# 不要用你的主数据库连接
AGENT_DB_URL = os.environ['READONLY_DATABASE_URL']

# 数据库侧建一个只读角色，这比在代码里判断可靠得多
# CREATE ROLE agent_ro LOGIN PASSWORD '...';
# GRANT CONNECT ON DATABASE app TO agent_ro;
# GRANT USAGE ON SCHEMA public TO agent_ro;
# GRANT SELECT ON ALL TABLES IN SCHEMA public TO agent_ro;
# 注意：不要 GRANT 任何 INSERT/UPDATE/DELETE
```

这一条比任何 prompt 里的「请不要修改数据」都可靠。**权限边界要在系统层强制，不要指望模型自觉** —— 这是 M13 讲护栏时的核心观点，用在自己产品上同样成立。

### 场景一：每日运营简报

最容易做也最先见效的一个。

```python
async def daily_brief() -> str:
    """收集数据 → 让模型写简报 → 邮件发给自己。"""
    data = {
        'funnel':    await q_funnel(days=1),        # L20-03 的漏斗
        'funnel_7d': await q_funnel(days=7),        # 对比基线
        'cost':      await q_cost_by_user(days=1),  # L18-05 的成本
        'errors':    await q_error_summary(days=1),
        'support':   await q_unanswered_count(),
        'changes':   await q_deploys(days=1),       # 昨天部署了什么
    }

    prompt = f"""你是这个一人产品的运营助手。基于下面的数据写一份 150 字以内的简报。

要求：
- 只写异常和变化，不要罗列所有数字（数字附在下面的原始表格里）
- 每条异常给出你认为最可能的原因，并明确标注这是推测
- 如果昨天有部署，优先检查指标变化和它的时间关系
- 没有异常就写「无异常」，不要为了凑内容硬找

数据：{json.dumps(data, ensure_ascii=False, default=str)}
"""
    summary = await llm.complete(prompt)
    return summary + '\n\n' + render_tables(data)
```

三条 prompt 约束值得注意：

**「只写异常和变化」** —— 否则模型会把所有数字复述一遍，你就不看了。简报的价值在于筛选。

**「明确标注这是推测」** —— 模型的归因经常是错的，但它提供的假设很有价值。标注清楚，你就不会把它当结论。

**「没有异常就写无异常」** —— 不加这条，模型会为了显得有用而制造问题。这是 LLM 的普遍倾向，在日报场景里特别有害，因为你会被训练成忽略它的输出。

### 场景二：支持邮件初筛与草拟

支持是最占时间的（L20-04），也是最适合半自动化的。

```python
CATEGORIES = ['故障', '卡点', '功能请求', '账单', '误解', '其他']

async def triage(email: dict) -> dict:
    prompt = f"""把这封用户邮件分类并起草回复。

分类候选：{CATEGORIES}
产品事实（回复中不得超出这些事实）：
{PRODUCT_FACTS}
常用模板：
{REPLY_TEMPLATES}

用户邮件：
{email['body']}

输出 JSON：
{{
  "category": "...",
  "urgency": "high|normal|low",
  "draft": "回复草稿",
  "uncertain": ["你不确定、需要开发者确认的点"],
  "product_issue": "如果这反映了一个产品问题，一句话描述；否则 null"
}}

严格要求：
- 不得承诺任何功能、时间点、退款或补偿
- 不确定的一律放进 uncertain，不要在草稿里编造
"""
    return json.loads(await llm.complete(prompt))
```

关键在最后那两条约束，以及 `uncertain` 这个字段的设计。

**承诺是不可撤回的。** 模型很容易顺着用户的期待说「这个功能我们下个版本会加上」，而你根本没这个计划。明确禁止，并且**所有草稿必须你点发送**。

**`uncertain` 字段是安全阀。** 它让模型有地方安放不确定性，而不是被迫编造。看到 `uncertain` 非空，你就知道这封要仔细看。

`product_issue` 字段则自动完成了 L20-04 里那件最容易被跳过的事 —— 把支持对话转成产品待办。攒够 3 条同类，自动升优先级。

### 场景三：成本异常检测

L18-05 讲过三种崩账行为。让 Agent 每天扫一遍，标记可疑账号，但**只标记不封禁**。

```python
async def cost_watch(threshold: float = 5.0):
    suspects = await q_high_cost_users(days=1, threshold=threshold)
    for s in suspects:
        pattern = await q_call_pattern(s['user_id'], days=1)
        verdict = await llm.complete(f"""判断这个账号的使用模式属于哪一类：
A. 正常重度用户（人工操作特征：间隔不规则、输入各不相同）
B. 接入了自动化脚本（间隔规律、频率超过人类可能）
C. 刷额度滥用（反复提交相同或近似内容）

数据：{pattern}
输出 JSON：{{"verdict":"A|B|C","confidence":0-1,"evidence":"..."}}
""")
        v = json.loads(verdict)
        await mark_account(s['user_id'], v)      # 只写标记表，不动订阅
        if v['verdict'] in ('B', 'C') and v['confidence'] > 0.7:
            notify_me(f"可疑账号 {s['user_id']}：{v['verdict']} — {v['evidence']}")
```

注意 `mark_account` 写的是一张独立的标记表，不碰订阅和权限。**封禁是不可逆的动作，误判一次就是失去一个真实付费用户** —— B 类（接入自动化脚本）尤其容易误判，而那类用户往往是你最有价值的用户，正确的处理是找他谈一个 API 档位，不是封了他。

### 场景四：反馈聚合

把散落在支持邮件、社区评论、流失回访里的反馈，定期聚合去重。

```python
async def weekly_feedback_digest():
    items = await q_feedback_items(days=7)   # L20-04 记录的结构化条目
    prompt = f"""把这些用户反馈聚类去重，输出前 5 组。

要求：
- 每组给出：问题描述、出现次数、代表性原话（引用，不要改写）
- 按「出现次数 × 影响程度」排序
- 明确区分「卡点」（用户想用但用不了）和「功能请求」（想要更多）
- 不要提出解决方案，只做归类

反馈条目：{items}
"""
    return await llm.complete(prompt)
```

「不要提出解决方案」这条约束很重要。模型给的方案通常很通用（「优化用户引导」），没有价值，还会让你误以为想过了。**归类交给它，判断留给你** —— 判断需要你对产品和取舍的理解，那部分不可委托。

### 别过度自动化

最后一条提醒，也是这一节最重要的一条。

**运营自动化会切断你和用户的接触。** L20-01 强调过一对一的价值，L20-04 强调支持是最好的洞察来源 —— 如果所有邮件都被 Agent 分好类、写好草稿，你只是点发送，那些信息就从你身边流过去了，你不会真正读进去。

一个务实的平衡：

- **前 100 个用户期间，支持不要自动化。** 你需要的不是效率，是理解。这个阶段每一封邮件都值得你亲自读完、亲自回。
- **监控、报表、成本检测可以尽早自动化。** 这些本来就是机械劳动，没有理解可言。
- **有了自动化之后，每周留一个「亲自读原始数据」的时段。** 不看简报，直接翻原始的支持邮件和用户反馈。摘要会滤掉那些还没被归类的东西 —— 而新的机会通常就藏在那里。

判断你是不是过度自动化了，有个信号：**你已经说不出最近三个用户分别是谁、遇到了什么问题**。到这一步，你就变成了自己产品的管理者，而一人公司的优势恰恰在于你不是管理者。

### 动手 5 分钟

搭一个最小的运营 Agent，从日报开始。

1. 建一个数据库只读角色，确认它执行 `UPDATE` 会被拒绝（在系统层验证，不是在 prompt 里）。
2. 写日报 Agent：拉昨天的漏斗、成本、错误三类数据，让模型写 150 字简报，发到你邮箱。prompt 里必须带上「只写异常」「标注推测」「无异常就说无异常」三条约束。
3. 列出你所有运营环节，按「全自动 / 半自动 / 不可自动」分三类，写下每一项的理由。

**验收标准**：只读角色的写操作在数据库层被拒绝（不是靠 prompt 约束），且你的「不可自动」清单里至少包含封禁、退款、对外承诺这三项。如果日报连续三天都在报「异常」，检查是不是漏了「无异常就说无异常」那条约束。

### 要点总结

- 一人公司的运营工作量按用户数增长；Agent 能填一部分缺口，但**边界由「错了的代价和谁承担」决定**，不由技术难度决定。
- 通用规则：**Agent 可以读、分析、起草，凡是「写到外面去」或「动到钱」的动作都要经过你**。
- **权限边界要在系统层强制**（只读数据库角色），不要指望 prompt 里的「请不要修改」。
- 日报 prompt 必须带三条约束：**只写异常、标注推测、无异常就说无异常**；最后一条防模型为显得有用而制造问题。
- 支持初筛用 **`uncertain` 字段做安全阀**，让模型有地方安放不确定性而不是编造；**所有草稿必须你点发送**。
- 成本异常**只标记不封禁**：封禁不可逆，而「接入自动化脚本」的用户往往最有价值，正确处理是谈 API 档位。
- 反馈聚合要求「**只归类不给方案**」—— 模型的通用方案没价值，还会让你误以为想过了。
- **前 100 个用户期间支持不要自动化**；过度自动化的信号是「你说不出最近三个用户是谁、遇到了什么问题」。
