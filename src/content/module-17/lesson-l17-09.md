## AI 生成代码的质量门禁与技术债管理

用 AI 写代码，产出速度大概能到手写的三到五倍。但**代码不是资产，是负债** —— 每一行都需要被理解、被维护、被在出事时快速定位。产出速度乘以三，意味着负债累积速度也乘以三。

::interactive{type="codeReviewFailures"}

这一节讲怎么在保住速度的同时，不让代码库在半年后变成一团你自己也读不懂的东西。

### AI 代码的特征性问题

AI 写的代码和新手写的代码坏法不一样。它的语法几乎不会错，风格通常还挺整齐，问题藏在别的地方。

**一、重复实现。** 你在第 3 周让它写了一个日期格式化函数，第 9 周又需要一个，它不知道前一个存在，于是又写一个。半年后你有五个功能重叠但行为微妙不同的工具函数，改 bug 时改了一个，其余四个还错着。

**二、过度防御。** 它爱写一大堆 try/except 和 null 检查，把真实错误全吞掉。表现是线上出问题时日志里什么都没有，因为所有异常都被 `except Exception: pass` 或者 `return None` 消化了。

**三、抽象错位。** 它会为一个只用了一次的地方建一个配置类、一个工厂、一个策略接口 —— 因为训练数据里的「好代码」长这样。但那是给团队协作和多变体场景准备的，你这里只有一个变体。

**四、隐式契约丢失。** 它删掉或改写某段代码时，不知道那段代码是为了修某个具体 bug 存在的。这条上一节讲过，代价最大。

**五、依赖膨胀。** 需要一个功能，它就 `pip install` 一个包。三个月后你的 `requirements.txt` 有 60 行，其中 20 个包各自只被用了一个函数。

这五类问题有个共同点：**单次 review 时都不明显**。每一次改动看起来都合理，问题是累积出来的。所以对付它们要靠机制，不能靠自觉。

### 门禁分三层

不要指望一层检查解决所有问题。按「谁来发现」分三层。

**第一层：机器能判的，交给 CI。**

```toml
# pyproject.toml
[tool.ruff.lint]
select = ["E", "F", "I", "B", "C90", "ARG", "SIM"]
# C90 = 圈复杂度，ARG = 未使用参数，SIM = 可简化的写法

[tool.ruff.lint.mccabe]
max-complexity = 10

[tool.mypy]
strict = true
warn_unused_ignores = true
disallow_untyped_defs = true
```

再加两条自定义检查，专治 AI 的毛病：

```bash
#!/usr/bin/env bash
# scripts/check-quality.sh
set -uo pipefail
fail=0

# 1. 禁止吞异常
if rg -n 'except\s+Exception:\s*(pass|return None)' src/; then
  echo '❌ 发现吞异常的写法，必须记录日志或向上抛'
  fail=1
fi

# 2. 依赖数量红线
n=$(grep -cve '^\s*#' -e '^\s*$' requirements.txt)
if [ "$n" -gt 30 ]; then
  echo "❌ 依赖数 $n 超过 30，新增依赖前先确认标准库做不到"
  fail=1
fi

# 3. 检测可能重复的工具函数（同名或高度相似的函数名）
rg -o 'def (format_|parse_|to_|from_)\w+' src/ -r '$1' \
  | sort | uniq -d | while read -r p; do
      echo "⚠️  前缀 $p 有多个实现，确认是否重复"
    done

exit $fail
```

`max-complexity = 10` 这条效果出奇地好。AI 很爱把一堆分支塞进一个函数，圈复杂度是最直接的信号。

**第二层：人能判但容易忘的，交给清单。**

```markdown
## AI 代码合并前自查

- [ ] 我能逐段解释这段代码在干什么（不能解释的删掉重来）
- [ ] 搜过了：这个功能仓库里是不是已经有了
- [ ] 新增依赖？→ 标准库真的做不到吗；这个包最近一年有更新吗
- [ ] 有 try/except？→ 每一个都记了日志或者重新抛出了
- [ ] 有新抽象（基类/工厂/接口）？→ 现在有几个实现？只有 1 个就删掉
- [ ] diff 里有删除的代码？→ 逐行确认那些代码不是在修某个 bug
```

第一条是整份清单的核心，也是 L17-01 那条纪律的落地：**不能解释的代码不进主干**。这条守住了，其余问题都是小问题；守不住，其余检查都是装饰。

**第三层：只有时间能暴露的，交给定期扫描。**

每月花半小时跑一遍：

```bash
# 大文件（AI 爱把东西堆进一个文件）
find src -name '*.py' -exec wc -l {} + | sort -rn | head -10

# 长函数
rg -U 'def \w+\([^)]*\):(\n(?!def ).*){80,}' src/ -l

# 各类记账
rg 'TODO\(debt\)' -A 3 src/

# 从没被 import 过的模块
for f in $(find src -name '*.py' | grep -v __init__); do
  m=$(basename "$f" .py)
  rg -q "import.*\b$m\b" src/ || echo "疑似死代码: $f"
done
```

### 一个具体的判断标准：能不能被解释

前面反复提到「能解释」，把它说得更具体一点，因为这是一人公司唯一真正可靠的质量标准。

「能解释」不是指你能读懂语法，是指对代码里的每一段，你能回答：

- 它为什么在这里（去掉会怎样）
- 它的输入范围是什么（什么情况下会拿到意外的值）
- 它坏掉的时候会怎么表现（报错？静默错误？慢？）

拿一段 AI 生成的代码验一验：

```python
async def fetch_with_retry(url: str, max_retries: int = 3) -> dict | None:
    for i in range(max_retries):
        try:
            async with httpx.AsyncClient(timeout=30) as client:
                r = await client.get(url)
                r.raise_for_status()
                return r.json()
        except Exception:
            if i == max_retries - 1:
                return None
            await asyncio.sleep(2 ** i)
    return None
```

看着挺规范。但按三个问题过一遍：

- 为什么 timeout 是 30？（不知道，AI 随手写的。上游 p99 是多少？没测过。）
- 什么情况下会拿到意外的值？（返回体不是 JSON 时 `r.json()` 会抛，被 except 吞掉，调用方拿到 None，无法区分「请求失败」和「返回了 null」。）
- 坏掉时怎么表现？（静默返回 None，日志里什么都没有。这是最坏的一种坏法。）

三问全军覆没。改法不复杂：

```python
async def fetch_with_retry(url: str, max_retries: int = 3) -> dict:
    """失败时抛出，由调用方决定降级策略。timeout 依据：上游 p99 = 8s，留 3x 余量。"""
    last_err: Exception | None = None
    for i in range(max_retries):
        try:
            async with httpx.AsyncClient(timeout=25) as client:
                r = await client.get(url)
                r.raise_for_status()
                return r.json()
        except (httpx.HTTPError, ValueError) as e:  # 只捕获预期的错误
            last_err = e
            logger.warning('fetch 第 %d 次失败 url=%s err=%s', i + 1, url, e)
            if i < max_retries - 1:
                await asyncio.sleep(2 ** i)
    raise RuntimeError(f'fetch 失败 {max_retries} 次: {url}') from last_err
```

区别不在代码量，在于现在每一行都能回答那三个问题。

### 债务优先级：按爆炸半径排

技术债不是均等的。排优先级用一个二维判断：**多久会爆** × **爆了多大**。

| | 爆了影响小 | 爆了影响大 |
|---|---|---|
| **短期会爆** | 顺手修 | **立刻修** |
| **长期才爆** | 记账不动 | 排进下个月 |

「爆了影响大」的判据很实在：会不会导致数据丢失、会不会多扣用户钱、会不会泄漏别人的数据、会不会让服务起不来。

这四类之外的债，包括「这段代码很丑」「这里应该抽象一下」「命名不好」，在你有稳定收入之前，**记账就够了，不用修**。一人公司的时间是最稀缺的资源，花在美学上的每一小时都是从功能和用户那里偷来的。

### 速度和质量的真实关系

有个说法是「用 AI 快速写完，以后再重构」。实践里这句话的后半句几乎不会发生 —— 因为「以后」总有更紧急的事。

更接近现实的框架是：**在生成时就设好约束的成本，远低于生成后修的成本**。前面几节讲的规格、约定文件、上下文工程、门禁清单，作用都是把质量成本前移到最便宜的那一刻。

一个粗略的量级感受：同样一处问题，在 Prompt 里约束掉花 1 分钟，在 review 时发现改掉花 10 分钟，合并后再重构花 1 小时，线上出事后修花半天加上用户流失。每往后推一步，成本涨一个量级。

### 动手 5 分钟

给你的代码库做一次质量体检，重点是找累积型问题。

1. 跑本节的扫描命令，列出最长的 3 个文件和最长的 3 个函数。
2. 随机挑一段 AI 生成的代码，用「为什么在这里 / 输入范围 / 坏了怎么表现」三问过一遍，记录答不上来的地方。
3. 搜一遍你的仓库有没有重复实现（同前缀的工具函数、两处功能一样的日期处理），至少找出 1 处。

**验收标准**：你能指出至少 1 处「单看没问题、放在一起才是问题」的累积型缺陷（重复实现、吞异常、只有一个实现的抽象）。如果三问全都答得上来，把范围扩大到最近一个月生成的代码 —— 这类问题通常藏在你当时觉得「先跑起来再说」的那几个文件里。

### 要点总结

- **代码是负债不是资产**：AI 让产出快三倍，负债累积也快三倍。
- AI 代码的五类特征性问题：**重复实现、过度防御（吞异常）、抽象错位、隐式契约丢失、依赖膨胀**。共同点是单次 review 看不出，靠机制不靠自觉。
- 门禁分三层：**CI 管机器能判的**（复杂度上限、类型、吞异常检测、依赖数红线），**清单管容易忘的**，**月度扫描管时间才能暴露的**。
- 唯一可靠的质量标准是「**能不能被解释**」：为什么在这里、输入范围是什么、坏了会怎么表现。三问答不上来就重写。
- **静默返回 None 是最坏的坏法** —— 调用方无法区分失败和空结果，日志里也没痕迹。
- 技术债按 **多久会爆 × 爆了多大** 排序；「代码很丑」「命名不好」这类债，有稳定收入前记账就够。
- 「先快后重构」的后半句基本不会发生。**把质量成本前移到 Prompt 约束里**，那是最便宜的一刻。
- 同一处问题：Prompt 约束 1 分钟 / review 发现 10 分钟 / 合并后重构 1 小时 / 线上出事半天加用户流失。**每往后推一步涨一个量级**。
