## AI 辅助测试与重构：让改动可验证

一个人做产品，最怕的不是写不出功能，是**不敢改**。

代码堆到三千行以后，每次动一处都心里发虚：这个改动会不会把别的地方弄坏？没有测试的时候，唯一的验证方式是手工点一遍，点五分钟，还只覆盖了你记得的那几条路径。于是你开始绕着老代码写新代码，重复逻辑越来越多，最后彻底不敢动。

::interactive{type="refactorDiffer"}

AI 在这件事上能帮很大的忙 —— 但方式和大多数人想的不一样。

### AI 写测试的真实水平

先说清楚它擅长什么、不擅长什么。

| 任务 | AI 表现 | 说明 |
|------|---------|------|
| 补齐已有函数的用例骨架 | 好 | 参数组合、类型边界，它比人有耐心 |
| 生成 mock 与 fixture | 好 | 样板代码，正是它的强项 |
| 想出「这个函数会怎么坏」 | 一般 | 能想到 null 和空数组，想不到业务上的坏 |
| 判断「这个行为对不对」 | 差 | 它会照着你的实现写断言，实现错了测试跟着错 |
| 端到端流程测试 | 差 | 需要环境上下文，它没有 |

最后一行的第二条是核心陷阱：**让 AI 读着你的实现去写测试，等于让它把 bug 也一起固化下来**。它会看到 `if x > 10` 就断言 `x=11 → True`，完全不会问「这里是不是应该 >=」。

所以顺序很重要：**先有期望的行为描述，再让它写测试；不要先有实现**。这也是 L17-03 讲的规格驱动开发在测试环节的延续 —— 规格里的边界情况表，就是最好的测试输入。

### 让 AI 从规格写测试，不从代码写测试

对比两种提示：

```
# 差：把实现丢进去
帮我给这个函数写测试：
def calc_discount(price, level, coupon): ...（贴了 40 行实现）
```

```
# 好：把规格丢进去
给 calc_discount 写 pytest 测试。它的规格是：

输入：price（分，正整数）、level（'free'|'pro'|'team'）、coupon（可选，字符串）
输出：折后价（分，正整数）

规则：
1. level 折扣：free 不打折，pro 打 9 折，team 打 8 折
2. coupon 在 level 折扣之后再叠加，coupon 面额固定为 500 分
3. 折后价不得低于 100 分，低于则取 100
4. coupon 无效或已用过时，忽略优惠券，不报错

边界情况：
- price = 100 且 level = team → 结果是 100（触发下限）
- price = 500 且有 coupon → 结果是 100（不是 0，触发下限）
- coupon = None 与 coupon = '' 行为一致

不要看实现，就按规格写。每条规则至少 1 个用例，每个边界情况 1 个用例。
```

第二种提示写出来的测试，能抓到实现里的错。第一种只能抓到实现和实现自己不一致的地方 —— 而那不存在。

### 覆盖率是个会骗人的指标

AI 很容易帮你把行覆盖率刷到 90%。但覆盖率高不等于测得好。

```python
# 覆盖率 100%，价值接近 0
def test_calc_discount():
    result = calc_discount(1000, 'pro', None)
    assert result is not None
```

这行代码走过了函数的每一行，断言却什么都没验证。AI 在被要求「提高覆盖率」时，非常容易产出这类测试。

更有用的提问方式是**按风险要测试**，而不是按覆盖率：

```
这个模块里哪些逻辑一旦出错，用户会直接受损失（多扣钱、数据丢失、看到别人的数据）？
针对这些逻辑各写 3 个用例：一个正常、一个边界、一个恶意输入。
其余部分不用测。
```

一人公司的测试策略应该是**倒金字塔式的重点覆盖**，不是均匀铺开：钱相关的逻辑、权限判断、数据删除，这三类必须有测试；UI 展示、格式化函数、日志，可以完全不测。

### 变更前的安全网：先固化现状

要重构一段没有测试的老代码，正确顺序不是「重构完再补测试」，而是**先给现状拍一张快照**。

```python
# 特征测试（characterization test）：不判断对错，只固化当前行为
import json, pytest
from app.pricing import calc_discount

CASES = [
    (1000, 'free', None),
    (1000, 'pro', None),
    (1000, 'team', 'SAVE500'),
    (100,  'team', 'SAVE500'),
    (0,    'pro',  None),
]

def test_snapshot(snapshot_file='tests/pricing_snapshot.json'):
    actual = {f'{a}|{b}|{c}': calc_discount(a, b, c) for a, b, c in CASES}
    expected = json.load(open(snapshot_file))
    assert actual == expected
```

这类测试不关心行为对不对，只关心**重构前后行为一致**。有了它，你就可以放心地让 AI 把三百行的函数拆成八个小函数 —— 拆完跑一遍，输出一样就说明拆对了。

让 AI 生成 CASES 列表很合适：让它读代码，列出所有分支的代表性输入。这正好是它擅长的机械活。

### 重构：一次只做一件事

AI 有个坏习惯：你让它「重构一下这个函数」，它会顺手把变量名改了、把循环换成推导式、把错误处理方式换了、还「优化」了一处它认为多余的判断 —— 而那处判断是你三个月前为了修一个线上 bug 加的。

改法是**显式限定改动范围**：

```
重构 calc_discount，只做一件事：把折扣计算和下限裁剪拆成两个函数。

禁止：
- 修改任何变量名
- 修改任何条件判断的逻辑
- 删除任何看起来多余的代码（它可能在修某个你不知道的 bug）
- 改变函数签名

拆完后 calc_discount 的输入输出行为必须完全不变。
```

「删除任何看起来多余的代码」这条尤其要写死。AI 看不到 git 历史，不知道某行代码是为了什么加的，它删掉的往往是最贵的那几行。

判断一个重构 PR 该不该合并，有个简单标准：**diff 里如果同时出现了「结构调整」和「逻辑修改」，退回去让它拆成两次**。混在一起的改动，出问题时你无法二分定位。

### 技术债的记账方式

AI 让写代码变快了，也让攒债变快了。一人公司没有 code review，债很容易攒到还不动。

有效的做法不是「定期重构」（永远排不上），而是**当场记账**：

```python
# TODO(debt): 这里的重试逻辑是硬编码的 3 次，没有退避。
# 触发条件：上游 429 频繁时会打爆对方。
# 修的时机：付费用户 > 50 或收到第一次限流告警。
# 估时：1h
```

三个要素缺一不可：**什么问题、什么时候会爆、什么时机修**。只写「这里以后要优化」的 TODO 等于没写。

每个月扫一遍这些 TODO，看有没有哪条的「触发条件」已经接近了。这比按日历安排重构靠谱得多，因为它把重构时机绑在了真实信号上。

```bash
# 一行命令看当前债务
rg 'TODO\(debt\)' -A 3 src/ | less
```

### 什么时候可以不写测试

诚实一点：一个人做早期产品，有些地方确实不值得写测试。

不写的判据是**改错了代价小且能快速发现**。比如一个只在管理后台用的报表页面，算错了你自己一眼能看出来，改回去也就两分钟 —— 这种地方写测试是净亏损。

必须写的判据是**改错了代价大或者发现得晚**：扣费金额、权限边界、数据删除、定时任务、和外部系统的对账逻辑。这些地方错了，你可能一个月后才从用户投诉里知道，那时已经错了一千条数据。

按这个判据分，早期产品大概 20% 的代码需要测试，80% 不需要。把力气花在那 20% 上，比追求覆盖率数字有用得多。

### 动手 5 分钟

挑你项目里最不敢改的那段代码，给它加一层安全网。

1. 让 AI 读这段代码，列出所有分支的代表性输入（只要输入，不要它判断输出对错）。
2. 跑一遍这些输入，把实际输出存成快照文件，写一个对比快照的测试。
3. 现在让 AI 做一次纯结构重构（拆函数），加上「禁止改逻辑、禁止改名、禁止删代码」的限定，跑快照测试验证。

**验收标准**：重构后快照测试通过，且 `git diff` 里看不到任何条件判断的变化。如果快照测试挂了，看清楚是重构改错了行为，还是你的快照本来就漏了某个分支 —— 两种情况的修法完全不同。

### 重点覆盖的测试模板：钱、权限、删除

一人公司的测试策略是"倒金字塔式重点覆盖"。钱、权限、删除三类必须有测试。下面是三个模板，每次 AI 生成相关代码，直接套用：

```python
"""tests/test_critical_paths.py —— 钱、权限、删除三类必须覆盖的测试模板"""

import pytest

# ============================================================
# 模板一：钱相关的测试
# ============================================================
class TestPaymentAmount:
    """任何涉及金额计算的地方，必须覆盖这四种情况。"""

    def test_zero_amount_not_charged(self):
        """金额为 0 时不应发起扣款。"""
        ...

    def test_negative_amount_rejected(self):
        """负金额输入应抛异常，不能静默处理。"""
        with pytest.raises(ValueError, match="金额"):
            ...

    def test_amount_rounding(self):
        """金额取整规则要明确：四舍五入、向上取整、还是向下取整？
        混用会导致对账不平。"""
        ...

    def test_currency_boundary(self):
        """货币最小单位边界（如 1 分钱）。"""
        ...


# ============================================================
# 模板二：权限相关的测试
# ============================================================
class TestAccessControl:
    """权限判断必须覆盖：有权限、无权限、跨用户、提权攻击。"""

    def test_owner_can_access(self):
        """资源所有者可以访问。"""
        ...

    def test_non_owner_cannot_access(self):
        """非所有者不能访问，返回 403 而不是 200（空列表也不行）。"""
        ...

    def test_admin_cannot_see_other_user_data(self):
        """管理员也不能直接看到用户私密数据——需要明确的审计日志。"""
        ...

    def test_privilege_escalation_blocked(self):
        """用户不能通过修改请求参数访问其他用户的数据（IDOR）。"""
        ...


# ============================================================
# 模板三：数据删除相关的测试
# ============================================================
class TestDataDeletion:
    """删除操作必须覆盖：软删除、关联清理、恢复、幂等。"""

    def test_soft_delete_preserves_data(self):
        """软删除后数据仍在（deleted_at 字段），只是查询不可见。"""
        ...

    def test_hard_delete_cleans_cascade(self):
        """硬删除后关联数据一并清理，不留孤儿记录。"""
        ...

    def test_double_delete_is_idempotent(self):
        """重复删除不报错，不产生副作用。"""
        ...

    def test_deleted_data_not_in_export(self):
        """已删除数据不应出现在导出/报表中。"""
        ...

    def test_delete_user_cleans_all_locations(self):
        """删除用户时，所有关联数据位置都要清理。
        漏掉一处就是一个合规风险。"""
        ...
```

这些模板不是一次写完的——用 AI 生成具体实现，但**模板里的测试类型必须由你来确认**。AI 不知道你的产品里"删除用户"涉及几张表，你知道。把模板复制到你的测试文件里，逐条填上你的具体断言。

### 要点总结

- 一个人做产品最贵的成本不是写不出来，是**不敢改**；测试的价值在于把「不敢」变成「敢」。
- **不要让 AI 读着实现写测试**，那只会把 bug 一起固化。先给规格，再让它写。
- **覆盖率会骗人**：走过每一行不等于验证了每一行。按风险要测试，不按覆盖率要测试。
- 一人公司的测试是**重点覆盖不是均匀铺开**：钱、权限、删除必测；UI、格式化、日志可以不测。
- 重构老代码先**用特征测试固化现状**，只保证前后一致，不判断对错 —— 生成用例列表正好是 AI 的强项。
- 限定 AI 的重构范围，尤其要写死「**禁止删除看起来多余的代码**」—— 它看不到 git 历史。
- diff 里**结构调整和逻辑修改不能混在一起**，混了就退回重做，否则出问题无法二分定位。
- 技术债要**当场记账**，写清「什么问题 / 什么时候会爆 / 什么时机修」，把重构时机绑在真实信号上而不是日历上。
