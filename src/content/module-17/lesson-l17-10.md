## 独立开发者的工具链与成本控制

这一节讲钱，但不是讲怎么定价（那是 M18 的事），是讲**在还没有收入的时候，怎么把每月固定支出压到你能长期承受的水平**。

这件事的重要性被严重低估。一人公司最常见的死法不是产品没人要，是**在找到付费用户之前钱就烧完了或者人先累垮了**。每月固定支出决定了你有多长的跑道，跑道长度决定了你能试错几次。
### 先算一个数：你的月度烧钱率

打开记账本，把和这个产品相关的所有月付项列出来。典型的一人 AI 产品，早期支出大概是这些：

| 类别 | 典型区间 | 备注 |
|------|---------|------|
| AI 编码工具订阅 | $20-200/月 | 差异极大，见下文 |
| 模型 API（开发用） | $5-50/月 | 自己调试消耗的 |
| 模型 API（用户用） | 随用户数变 | 这部分归入单位经济，见 M18 |
| 服务器 | $5-40/月 | 早期一台小 VPS 够了 |
| 数据库 | $0-25/月 | 托管 Postgres 或自建 |
| 对象存储 | $0-5/月 | 早期几乎免费 |
| 域名 | ~$1/月 | 年付摊薄 |
| 邮件发送 | $0-20/月 | 免费额度通常够早期用 |
| 监控/日志 | $0-30/月 | 免费层能撑很久 |
| 支付通道 | 按比例抽成 | 无固定费，见 M18 |

把你的数字填进去，得到月度烧钱率 `B`。再看你手里能投入这件事的钱 `M`，跑道就是 `M / B` 个月。

这个数字要**具体到月**。「我大概还能撑一阵」和「我还有 14 个月」是完全不同的两种心理状态，后者能让你做出更理性的取舍。

### 编码工具：按使用模式选，不按名气选

AI 编码工具的支出弹性最大，$20 和 $200 都能用，差别值不值得取决于你的使用模式。

三种典型模式：

**探索型**（每天大量试错、来回改方案）：token 消耗高，适合包月不限量的订阅制。按量付费在这种模式下会失控。

**执行型**（规格已经想清楚，只是让它写出来）：消耗相对可控，按量付费往往更划算，而且用便宜模型就够 —— 写一个已经描述清楚的函数，不需要最强的推理能力。

**混合型**（大部分时间执行，偶尔啃硬骨头）：最常见。合理配置是一个便宜的日常档 + 需要时临时调用贵的。

有个具体的省钱手法：**把任务按难度分档，默认走便宜模型，只在明确卡住时升档**。M1 讲过模型选型与档位划分的逻辑（nano/small/mid/large 四档的适用场景），那套判断在这里同样适用 —— 补一个已有函数的测试、改一个变量名、写一段 CRUD，用最便宜的档位完全够；设计一个新模块的接口、排查一个诡异的并发 bug，才值得上最贵的。

粗略估：一半以上的编码任务可以走便宜档，做这个分流量级上通常能砍掉 40%-60% 的 token 支出（量级示意，实际比例因任务分布而异）。

另一个容易忽略的：**上下文长度直接乘在成本上**。每次把整个仓库塞进去，比精准给三个文件贵一个量级，而且效果更差（L17-04 讲过上下文污染）。控制上下文既省钱又提升质量，是少见的双赢。

### 基础设施：从最小开始，别提前扩容

一个常见的浪费是照着「未来会有很多用户」的假设配基础设施。实际情况是，早期你的用户数大概率是个位数，一台 $5-10 的 VPS 能撑到几百个日活。

早期的合理配置：

```
一台 2C4G 的 VPS
  ├─ 应用容器
  ├─ Postgres（同机，定时备份到对象存储）
  └─ Caddy（自动 HTTPS）
```

同机部署数据库在生产上通常不推荐，但在「零收入、个位数用户」阶段，它的风险是可控的（数据量小、恢复快），而省下的钱是实打实的。等有了付费用户，第一笔该花的钱就是把数据库挪出去 + 加自动备份。

**备份是唯一不能省的那一项。** 一个人做产品，数据丢了没有任何人能帮你恢复。最小方案：

```bash
#!/usr/bin/env bash
# backup.sh —— 每天跑一次，成本约等于零
set -euo pipefail
D=$(date +%F)
pg_dump "$DATABASE_URL" | gzip > "/tmp/db-$D.sql.gz"
rclone copy "/tmp/db-$D.sql.gz" "r2:my-backups/"
rm "/tmp/db-$D.sql.gz"
# 保留 30 天
rclone delete "r2:my-backups/" --min-age 30d
```

写完之后**必须做一次恢复演练**。没验证过的备份不算备份 —— 这是个非常常见的翻车点：备份跑了半年，出事时才发现 dump 一直是空的。

### 免费额度的正确用法和陷阱

很多服务有慷慨的免费层，早期该用就用。但有两个陷阱。

**陷阱一：超额自动扣费。** 有些服务超出免费额度后不是停止服务，而是开始按量计费。如果你的接口被爬虫或者恶意请求打了一晚上，早上起来可能看到一张四位数的账单。

对策是**凡是能设支出上限的地方都设上**，设不了上限的服务就不要把关键路径放上去。同时在自己的应用层加限流 —— 这个是你能完全控制的：

```python
from collections import defaultdict
import time

_hits: dict[str, list[float]] = defaultdict(list)

def rate_limit(key: str, limit: int, window: int = 60) -> bool:
    """简单滑动窗口。早期够用，有量了再换 Redis 版。"""
    now = time.time()
    _hits[key] = [t for t in _hits[key] if now - t < window]
    if len(_hits[key]) >= limit:
        return False
    _hits[key].append(now)
    return True
```

**陷阱二：锁定。** 用某家的专有能力（特殊的数据库扩展、私有的部署格式、绑死的鉴权体系）越深，以后涨价时你越走不掉。判断方法很简单：**问自己「如果这家明天涨价 5 倍，我需要多久能搬走」**。超过一周的，说明绑得太深，值得在早期就留个抽象层。

不必为了防锁定而拒绝所有托管服务 —— 那样自己维护的时间成本更高。合理的做法是：数据（数据库、对象存储）要能搬，计算（跑在哪台机器上）可以绑。

### 时间是最贵的成本

上面所有的钱加起来，可能一个月两三百美元。而你投入的时间，按你本来能挣到的时薪算，是这个数字的几十倍。

所以有一类支出是明确该花的：**能明显省时间的工具，几乎总是划算的**。托管数据库比自己运维 Postgres 贵 $20/月，但省下的每月两小时运维时间远超这个价。

反过来，有一类时间投入是明确该砍的：**为了省几十块钱而自己搭一套东西**。自建监控、自建 CI runner、自己写部署系统 —— 这些在有团队时是合理的分工，在一个人时是纯粹的时间黑洞。

判断公式很粗糙但够用：

```
如果 (每月省下的小时数 × 你的时薪) > 月费，就买。
```

一人公司里，这个不等式在绝大多数工具上都成立。真正该省的是**订阅了但不用的东西** —— 每季度扫一遍账单，砍掉上个季度没打开过的服务，通常能砍掉三分之一。

### 一份最小工具清单

不推荐具体品牌（都会变），只说需要覆盖的类别和选择原则：

| 需要什么 | 选择原则 |
|---------|---------|
| 代码托管 + CI | 免费层够用即可，别为高级功能付费 |
| 应用托管 | 支持容器 + 能一键回滚 |
| 数据库 | 有自动备份，能导出标准 dump |
| 对象存储 | 兼容 S3 协议（保证可迁移） |
| 域名 + DNS | 与其他服务解耦，单独买 |
| 错误监控 | 免费层够用，关键是要真的接上 |
| 邮件发送 | 事务邮件和营销邮件分开发 |
| 支付 | 见 M18 |

「兼容 S3 协议」那条是防锁定原则的具体化：只要接口标准，换供应商就是改一行配置。

### 动手 5 分钟

算清楚你的跑道，找出可以砍掉的支出。

1. 列出所有和这个产品相关的月付项，算出月度烧钱率 `B` 和跑道 `M / B`（精确到月）。
2. 逐项问：这一项如果砍掉，我每月要多花多少时间？把「省的钱 < 多花的时间价值」的项标出来（这些不该砍）。
3. 找出最近 30 天你一次都没打开过的付费服务，砍掉。

**验收标准**：你能说出一个具体的跑道月数，并且指出至少 1 项「该砍」和 1 项「不该砍但你之前想砍」的支出。如果算下来跑道少于 6 个月，那么在 M18 讲的收款闭环就不是「以后再说」而是当前最优先的事。

### 要点总结

- 一人公司的常见死法不是产品没人要，是**在找到付费用户前钱烧完或人累垮**；月度烧钱率决定跑道长度，跑道长度决定试错次数。
- 跑道要**精确到月**。「大概还能撑一阵」和「还有 14 个月」是两种完全不同的决策状态。
- 编码工具按**使用模式**选：探索型适合包月不限量，执行型适合按量 + 便宜模型，混合型做难度分流。
- **按难度分档默认走便宜模型**，通常能砍掉 40%-60% 的 token 支出；控制上下文长度既省钱又提升质量。
- 基础设施**从最小开始**，别按「未来很多用户」提前扩容；一台小 VPS 能撑到几百日活。
- **备份是唯一不能省的**，而且必须做恢复演练 —— 没验证过的备份不算备份。
- 免费额度两个陷阱：**超额自动扣费**（凡能设上限都设，应用层自己加限流）和**供应商锁定**（数据要能搬，计算可以绑）。
- **时间比钱贵得多**：能明显省时间的工具几乎总该买；真正该省的是订阅了却不用的东西，每季度扫一遍账单。
