## AI Coding 的能力边界：什么该交给 AI，什么必须自己写

前 16 个模块，你学的是**怎么造 Agent**。这一章换个方向：**怎么用 AI 造软件**。两件事看起来相邻，技能栈只有一半重叠——造 Agent 是把 LLM 装进系统里，用 AI Coding 是把 LLM 装进你自己的工作流里。

对独立开发者来说，后者才是生死线。你没有团队，最稀缺的资源是时间。AI Coding 的价值从来不是"写得快"——写代码本来就不是软件开发里最耗时的部分。它真正的价值是：**让一个人能维护住本来需要三个人才维护得住的代码量**。

但这个价值只有在你划清边界之后才成立。边界没划清的人，用 AI 写出一堆自己看不懂的代码，三个月后被迫重写——那不是提效，那是把债务提前借出来了。

### 先看一组不那么令人愉快的观察

把"AI 能不能写这段代码"和"这段代码写完之后谁来维护"分开问，结论会很不一样：

| 任务 | AI 生成质量 | 你的维护成本 | 该不该交出去 |
|------|------------|-------------|-------------|
| 写一个 CSV 解析函数 | 高 | 低（有测试就行） | 交 |
| 写一个 React 表单组件 | 中 | 中（要读懂才能改） | 交，但要约束 |
| 设计数据库 schema | 中 | 极高（改起来要迁移） | 自己定，让 AI 补细节 |
| 决定用哪个消息队列 | 低 | 极高（选错要重构） | 自己决定 |
| 修一个你没复现的 bug | 低 | 极高（可能治标不治本） | 自己先定位 |
| 写单元测试 | 高 | 低 | 交 |
| 定义模块边界与依赖方向 | 低 | 极高 | 自己定 |

一个很清晰的规律浮出来了：**AI 擅长的是"局部的、可验证的、写错了容易发现的"工作**；它不擅长的是"全局的、影响深远的、写错了半年后才爆的"工作。

这条规律不是关于智力的，是关于反馈周期的。一个函数写错了，测试当场变红；一个模块边界划错了，你要到第八个功能加不进去的时候才知道。AI 拿不到后者的反馈，所以它在后者上的判断只能靠训练数据里的"常见做法"——而你的项目未必常见。

### 三类工作，三种委托方式

**第一类：全权委托。** 输入输出明确、有客观验收标准、错了立刻能发现。

```python
# 这类任务直接给需求就行
# "写一个函数，把 ISO 8601 时间字符串解析成带时区的 datetime，
#  无法解析时抛 ValueError 并在消息里说明是哪一位出错"
```

判据是：**你能在 30 秒内判断它写对了没有**。能，就交。

**第二类：受限委托。** AI 写，但你得先给约束。典型是 UI 组件、API 端点、数据模型这类"有很多种写法都能跑，但只有一种符合你项目风格"的东西。

约束的形式通常是三样：一份项目约定文件、一两个参考实现、一组必须通过的测试。这三样不给，AI 会每次给你一个新流派的代码，三个月后你的代码库像是六个人写的——而其实只有你一个人。

**第三类：不可委托。** 架构决策、模块边界、数据模型、依赖方向、以及任何"改起来需要数据迁移"的东西。

这类工作 AI 可以参与讨论——让它列方案、找漏洞、扮演反方，都很有用。但**拍板的必须是你**，因为承担后果的是你。

### 一个具体的分界例子

假设你要给产品加"用户可以给内容打标签"这个功能。

不可委托的部分（你自己想清楚，通常 20 分钟）：

- 标签是全局共享还是每个用户私有的？（决定了 schema 和后续所有查询）
- 标签数量有没有上限？（决定了要不要做分页）
- 删除标签时，已打标的内容怎么办？（决定了外键策略）

受限委托的部分（给约束后交给 AI）：

- 数据库迁移脚本（约束：项目用 Alembic，命名规范如下……）
- API 端点（约束：参照 `routers/notes.py` 的风格，鉴权用现有的 `current_user` 依赖）
- 前端标签选择器（约束：用项目的设计 token，支持键盘操作）

全权委托的部分：

- 标签名的规范化函数（去空格、转小写、去重复、长度截断）
- 上述所有代码的单元测试

你会注意到，那 20 分钟的"不可委托"部分，决定了后面 80% 的工作能不能顺利交出去。**想清楚再委托，比委托出去再返工便宜得多。**

### "看起来能跑"是最贵的陷阱

AI 生成的代码有一个特点：**它几乎总是能跑**。这比"跑不了"危险得多。

跑不了的代码，你会立刻改。能跑但有问题的代码，你会合并进主干，然后在三个月后的某个深夜里为它熬夜。

最常见的四种"能跑但有问题"：

**一、只处理了 happy path。** 网络失败、空数据、并发写入这些分支，AI 不主动写——因为你的需求里没提。

**二、悄悄引入了新依赖。** 为了实现一个日期格式化，它 import 了一个 300KB 的库。它不知道你在意包体积。

**三、重新实现了项目里已有的东西。** 你的 `utils/text.py` 里已经有 `slugify`，它又写了一个。半年后你有五个 slugify，行为各不相同。

**四、抽象层次不对。** 为了一个只会用一次的功能，它写了一个可插拔的策略模式框架——因为训练数据里"好代码"长这样。

这四种问题共同的特征是：**代码本身没错，错的是它和你项目的关系**。而"项目的关系"这件事，只有你知道。

### 委托清单：把边界写下来

抽象的原则记不住，写成清单才会执行。建议在项目根目录放一份 `AI_BOUNDARIES.md`，内容大概是这样：

```markdown
## 可以直接生成
- 纯函数、数据转换、格式化
- 单元测试（但断言我要看一遍）
- 一次性脚本（数据迁移、批量处理）
- 文档、注释、commit message

## 生成前必须给约束
- 任何 UI 组件 → 附上 design token 与一个参考组件
- 任何 API 端点 → 附上现有 router 文件作为范例
- 任何数据库操作 → 附上现有 model 定义

## 我自己写 / 我自己定
- 数据库 schema 与迁移策略
- 模块边界与依赖方向
- 第三方服务选型
- 任何涉及钱、权限、用户数据删除的逻辑

## 红线（AI 产出必须逐行读完才能合并）
- 支付相关
- 鉴权与权限判断
- 任何会删除数据的代码
```

这份清单最大的作用不是约束 AI，是**约束你自己**——在赶进度的深夜，你会想把红线里的东西也交出去。写下来的清单会拦你一下。

### 效率的真实来源

很多人对 AI Coding 的期待是"代码写得快 10 倍"，然后失望地发现只快了 1.5 倍。这个落差来自对软件开发的误解：写代码本来就只占开发时间的一小部分。

对独立开发者来说，AI 真正节省时间的地方其实是这几个：

**一、消除"不熟悉的技术栈"的启动成本。** 你没写过 Stripe 集成，以前要读两小时文档，现在半小时能跑通第一版。这是真实的、巨大的节省。

**二、把"我知道该怎么做但懒得做"的事变得不那么讨厌。** 补测试、写文档、改错误处理——这些事的心理阻力比技术难度大得多，AI 把阻力降下来了。

**三、维持代码质量的边际成本下降。** 以前"这个函数应该拆开但算了"，现在真的会拆。质量不再是时间的对立面。

**四、随时可用的第二意见。** 一个人开发最缺的是有人说"你这个设计有个问题"。AI 扮演这个角色是及格线以上的。

反过来，AI **不能**帮你解决的：知道该做什么产品、知道用户到底要什么、有耐心把一件事做完。这三样恰好是独立开发成败的主要因素——所以别指望工具能解决方向问题。

### 一个常见的反直觉建议：慢一点

用 AI Coding 最容易出的问题是**推进速度超过了你的理解速度**。

代码库以每天 500 行的速度增长，而你只读懂了其中 200 行。这个差值会累积，三周后你面对的是一个"我的项目但我不熟"的代码库——这是独立开发者最糟糕的处境，因为没有第二个人能帮你。

一条实用的纪律：**合并进主干的代码，你必须能向别人解释每一段在做什么**。做不到就先别合，先读懂。这条纪律会让你短期变慢，但它是让 AI Coding 在第三个月依然有效的唯一办法。

### 动手 5 分钟

给你手上的项目写一份 `AI_BOUNDARIES.md`。

1. 按"可直接生成 / 需要约束 / 我自己写 / 红线"四栏，各填至少 3 条。
2. 回顾你最近一次用 AI 写的代码，判断它属于哪一栏，以及你当时有没有按这一栏的方式处理。
3. 找出你项目里最不该被 AI 碰的那个文件（通常是钱、权限或数据删除相关），在文件顶部加一行注释说明原因。

**验收标准**：你的"红线"那一栏不是空的。如果你觉得没有任何代码是红线，说明你的项目还没到有人会因为它受损失的阶段——或者你低估了风险。

### 用代码检查委托边界：一个规则验证脚本

光写在 `AI_BOUNDARIES.md` 里容易忘。写一个简单的规则检查脚本，在 pre-commit 时自动触发——让机器帮你守住你写下的边界：

```python
"""scripts/check_boundaries.py —— 检查代码是否越过了 AI_BOUNDARIES.md 定下的红线"""

import sys
from pathlib import Path

# 红线目录：这些目录下的文件必须自己写，检出 AI 生成痕迹则告警
REDLINE_DIRS = ["billing/", "auth/", "permissions/"]

# AI 常犯的坏习惯，在红线目录中出现则告警
REDLINE_PATTERNS = [
    ("# TODO: 完善错误处理", "占位注释——在红线代码里不允许"),
    ("except Exception:", "裸 except Exception——请指定具体异常类型"),
    ("import openai", "疑似引入 AI SDK——请确认是否在允许列表"),
    ("import anthropic", "疑似引入 AI SDK——请确认是否在允许列表"),
]

def check_file(filepath: Path) -> list[str]:
    issues = []
    content = filepath.read_text(encoding="utf-8")
    for pattern, msg in REDLINE_PATTERNS:
        if pattern in content:
            issues.append(f"  {filepath}: {msg} (匹配: {pattern})")
    return issues

def main():
    all_issues = []
    for red_dir in REDLINE_DIRS:
        for f in Path(red_dir).rglob("*.py"):
            all_issues.extend(check_file(f))

    if all_issues:
        print("以下红线目录文件存在可疑内容：")
        for issue in all_issues:
            print(issue)
        print("红线代码必须自己写，请检查上述问题后再提交。")
        sys.exit(1)

    print("边界检查通过。")
    sys.exit(0)

if __name__ == "__main__":
    main()
```

这个脚本放在 `.husky/pre-commit` 里（L17-14 会讲怎么配置），每次提交前自动跑。**比贴在墙上的规则可靠**——墙上的规则会在赶进度时被忽略，pre-commit 的阻断不会。

### 要点总结

- **AI Coding 的价值不是写得快，是让一个人维护得住更大的代码量**——所以判断标准应该是维护成本，不是生成速度。
- AI 擅长"局部、可验证、错了立刻发现"的工作，不擅长"全局、影响深远、半年后才爆"的工作。区别在反馈周期，不在智力。
- 三类委托方式：全权委托（30 秒内能验证）、受限委托（先给约定+参考实现+测试）、不可委托（架构、边界、数据模型、任何要迁移的东西）。
- "能跑但有问题"比"跑不了"危险得多。四种典型：只写 happy path、悄悄加依赖、重复造轮子、抽象层次不对——代码本身没错，错的是它和你项目的关系。
- 把边界写成 `AI_BOUNDARIES.md`。它约束的主要不是 AI，是赶进度时的你自己。
- 真实的效率来源是：消除陌生技术栈的启动成本、降低补测试写文档的心理阻力、让质量不再是时间的对立面、提供随时可用的第二意见。
- **纪律：合并进主干的代码，你必须能解释每一段。** 推进速度超过理解速度是独立开发者最危险的处境。
