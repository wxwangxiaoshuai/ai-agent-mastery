## AI 生成生产级前端 UI（下）：状态、可访问性与响应式

上一节把「长什么样」约束住了。这一节处理更难的一半：**同一个界面在不同情况下长什么样**。

一个列表页，AI 默认给你的是「有 20 条数据、网络正常、鼠标可用、1440px 宽」的那一格。剩下几十格它不会主动想，而用户恰恰是在那几十格里骂人的。

### 界面不是一个样子，是一张矩阵

把任何一个界面拆成两个维度：**组件类型 × 运行状态**。

状态至少有这些：理想态、空态、加载中、部分加载、错误、内容超长、离线、无鼠标（纯键盘/读屏）。八种状态乘上你页面里的组件类型，就是一张几十格的矩阵。

AI 生成的代码，稳定地只覆盖其中的「理想态」那一列，偶尔带一个 loading。下面这张表可以点开每一格看：哪些是 AI 会自动给你的，哪些漏了会付出什么代价，以及要让它补上，Prompt 里该写哪一句。

::interactive{type="uiStateMatrix"}

用法不是把 40 格全填满 —— 那是过度工程。用法是**逐格做一次决定**：这一格我要做、还是明确不做。做，就写进 Prompt；不做，就在代码里留一行注释说明为什么。最怕的是从来没想过。

### 把状态写进 Prompt，而不是事后补

对比两种要求方式。

先看常见的写法：

```
帮我写一个用户列表页，展示头像、昵称、注册时间，支持分页。
```

你会拿到一个只有理想态的组件。然后你手工补 loading，补空态，补报错，补到一半发现骨架屏的高度和真实行高对不上，页面在数据回来的瞬间跳一下。

换成这样：

```
写一个用户列表页组件。

数据接口：GET /api/users?page=n，返回 { items: User[], total: number }
User = { id: string; avatar: string | null; name: string; createdAt: string }

必须显式处理以下状态，每种状态都要有对应 UI：
1. loading：骨架屏，行数 = 10，单行高度必须与真实行一致（56px），避免数据回来时布局跳动
2. empty（total === 0）：图标 + 「还没有用户」+ 一个「邀请用户」按钮
3. error：错误文案 + 「重试」按钮，重试调用同一个 fetch 函数
4. avatar 为 null：显示昵称首字母占位，不要显示裂图
5. name 超过 20 字符：单行截断加省略号，title 属性保留全文
6. 分页：total <= pageSize 时不渲染分页器

不要引入任何 UI 组件库。样式只用 tailwind.config.js 里已有的 token。
```

第二种写法长得多，但它是**一次性成本**，而且这段文字后面可以直接变成验收清单和测试用例。第一种写法的代价分摊在接下来两周的每一次 bug 修复里。

### 状态机比布尔标志可靠

AI 很爱写这种：

```tsx
const [loading, setLoading] = useState(false)
const [error, setError] = useState<string | null>(null)
const [data, setData] = useState<User[] | null>(null)
```

三个布尔/可空变量，理论上有 2×2×2 = 8 种组合，其中至少 4 种是非法的（比如 loading 且 error 且有 data）。非法状态一旦出现，界面就会同时显示骨架屏和错误提示，或者旧数据和新报错叠在一起。

要求它用**判别联合**：

```tsx
type ListState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; items: User[]; total: number }
  | { status: 'error'; message: string; retry: () => void }

const [state, setState] = useState<ListState>({ status: 'idle' })
```

渲染变成一次穷尽匹配：

```tsx
switch (state.status) {
  case 'idle':
  case 'loading':
    return <ListSkeleton rows={10} />
  case 'error':
    return <ErrorPanel message={state.message} onRetry={state.retry} />
  case 'success':
    return state.total === 0
      ? <EmptyState />
      : <List items={state.items} total={state.total} />
}
```

好处不只是少写 if。TypeScript 会在你加一个新 status 却忘了处理时直接报错 —— 这是把「状态覆盖」从人的自觉变成了编译器的检查。这条值得写进你的 `CONVENTIONS.md`：**异步 UI 一律用判别联合，禁止 loading/error/data 三件套**。

### 可访问性是约束，不是补丁

「先做完再加 a11y」在实践里等于「永远不加」。因为可访问性不是一层可以刷上去的漆，它影响 DOM 结构本身 —— 一个用 `div onClick` 做的按钮，要改成可访问的，得动结构。

给 AI 的基线约束，四条就能覆盖大部分场景：

```
可访问性要求（必须遵守，不是可选项）：
- 可点击元素一律用 <button>，禁止 <div onClick>。需要链接语义时用 <a href>。
- 所有仅有图标的按钮必须有 aria-label 描述动作（如 aria-label="删除该用户"）。
- 表单控件必须有关联的 <label htmlFor>，placeholder 不算标签。
- 焦点样式不得移除。禁止 outline: none 且不提供替代的 focus-visible 样式。
```

再加一条更狠的验收方式：**拔掉鼠标走一遍**。用 Tab 键从页面顶部走到你要完成的操作，如果中途焦点消失（跑进了 `display: none` 的元素）、或者你看不出当前焦点在哪、或者某个操作根本 Tab 不到，就是没过。

这个测试不需要任何工具，两分钟能做完，能抓到八成的低级问题。

对话框还有一条额外的：打开时焦点必须移进对话框，关闭时必须回到触发它的那个按钮，Esc 必须能关。这三条 AI 基本不会主动做，你得点名。

### 响应式：先说断点，再说行为

只说「要响应式」，AI 会给你堆一串 `md: lg: xl:`，看着像那么回事，实际在 768px 那个尴尬宽度下布局崩掉。

有效的说法是**声明断点和每个断点下的行为**：

```
断点行为（Tailwind 默认断点）：
- < 640px：单列。表格改为卡片列表，隐藏「注册时间」列。
  侧边栏改为顶部抽屉，默认收起。
- 640-1024px：两列。侧边栏收窄为图标条（w-16），仅显示图标 + tooltip。
- >= 1024px：三列。侧边栏完整展开（w-64）。

约束：
- 移动端可点击区域最小 44×44px。
- 不要用固定宽度 px 做容器，用 max-w-* + w-full。
- 横向不允许出现滚动条，长内容用截断或换行处理。
```

最后那条特别重要。移动端最常见的崩法就是某个不换行的长字符串（URL、订单号、用户填的一串字母）把整个页面撑宽，导致全页横向滚动。要求它对所有用户可输入的文本字段加 `break-words` 或 `truncate`。

自检方式同样不需要工具：浏览器开发者工具切到 375px 宽，从上往下滚一遍，看有没有横向滚动条、有没有被切掉的按钮、文字有没有小到看不清。

### 一份可以贴在显示器上的验收清单

每次 AI 交付一个界面，走一遍这个清单再合并：

```markdown
## UI 验收清单

### 状态
- [ ] 加载态存在，且骨架尺寸与真实内容一致（不跳动）
- [ ] 空态存在，且给出了下一步动作（不是只写「暂无数据」）
- [ ] 错误态存在，且可重试
- [ ] 长文本（>50 字）不撑破布局
- [ ] 图片加载失败有占位，不显示裂图

### 可访问性
- [ ] 纯键盘可完成主流程（Tab 走一遍）
- [ ] 焦点可见
- [ ] 图标按钮有 aria-label
- [ ] 表单有 label
- [ ] 对话框：焦点进入 / Esc 关闭 / 关闭后焦点归位

### 响应式
- [ ] 375px 下无横向滚动
- [ ] 375px 下主操作按钮可点（≥44px）
- [ ] 768px 下布局不错位

### 一致性
- [ ] 只用了设计 token 里的颜色/间距
- [ ] 没有新引入的 UI 依赖
```

这份清单比「看着还行」可靠，也比引入一整套自动化测试便宜。等你有付费用户了，再把其中稳定的几条（比如无横向滚动、焦点可见）用 Playwright 固化成回归测试。

### 什么时候该停

一个人做产品，UI 的投入要卡在一个具体的线上：**功能可用、状态不吓人、键盘走得通、手机上不崩**。超过这条线的打磨（微交互动效、暗色模式的第三种色阶、加载动画的缓动曲线）在你有稳定收入之前基本不产生回报。

判断标准也很具体：如果一个陌生用户在你的界面上卡住并且说不清为什么卡住，那是必须修的；如果他能顺利用完只是觉得「不够漂亮」，那先放着。

### 动手 5 分钟

挑你项目里最复杂的一个页面，用上面的矩阵做一次状态审计。

1. 列出这个页面涉及的所有组件类型（列表、表单、搜索框……），对每个组件走一遍八种状态，标记「已实现 / 未实现 / 明确不做」。
2. 把「未实现」里你决定要做的那些，改写成一段 Prompt 约束（照着本节第二部分的格式），交给 AI 生成补丁。
3. 拔掉鼠标，只用 Tab 和 Enter 走一遍这个页面的主流程，记录卡住的位置。

**验收标准**：你能说出这个页面有多少格状态、其中多少格是你**主动决定不做**的（而不是没想到）；键盘走查至少暴露 1 处此前没注意到的问题。如果键盘走查一路顺畅，多半是你走得太快 —— 重点看焦点在对话框和下拉菜单里的行为。

### 要点总结

- **界面不是一个样子，是组件类型 × 运行状态的一张矩阵**，AI 稳定只覆盖「理想态」那一列。
- 目标不是填满矩阵，而是**逐格做决定**：做，写进 Prompt；不做，注释说明原因。最怕从没想过。
- 状态要求**写进生成 Prompt**，不要事后补。这段文字本身就能复用为验收清单和测试用例。
- 异步 UI 用**判别联合**代替 loading/error/data 三件套，让编译器帮你守住状态覆盖。
- 可访问性是**结构约束不是补丁**：语义化元素、aria-label、label 关联、焦点可见，四条覆盖大部分场景。
- **拔掉鼠标 Tab 走一遍**，两分钟，抓八成低级问题，不需要任何工具。
- 响应式要**声明断点和每个断点的行为**，而不是笼统说「要响应式」；重点防长字符串撑破布局。
- UI 投入卡在「可用、状态不吓人、键盘走得通、手机上不崩」；**用户卡住必须修，用户只是觉得不够漂亮先放着**。
