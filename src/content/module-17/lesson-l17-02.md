## 从想法到方案：用 AI 做头脑风暴与可行性验证

独立开发者最贵的成本不是服务器，是**在错误的想法上花掉的三个月**。而这三个月的浪费，往往在写第一行代码之前就注定了——因为"我想做个东西"和"这个东西该怎么做"之间，隔着一堆没被问出口的问题。

这一节讲怎么用 AI 把这段距离压缩：不是让它替你想，是让它逼你想清楚。

### 为什么"和 AI 聊想法"经常没用

大多数人和 AI 讨论产品想法的过程是这样的：

> 我：我想做一个用 AI 帮人整理读书笔记的工具，你觉得怎么样？
>
> AI：这是个很棒的想法！读书笔记整理确实是很多人的痛点。你可以考虑以下功能：自动摘要、知识图谱、间隔重复……

聊完感觉很好，然后开始写代码，三个月后发现没人用。

问题出在提问方式上。你问的是"你觉得怎么样"，这是个**征求认可的问题**，而模型在这类问题上有强烈的附和倾向。它会给你一个热情的、结构完整的、看起来很专业的回答——里面没有任何能让你改变主意的信息。

要拿到有用的输出，你得改成**征求反对的问题**。

### 把附和倾向掰过来的三种提问

**一、指定角色与立场。**

> 你是一个投资过 30 个失败的工具类产品的天使投资人。我要做一个用 AI 整理读书笔记的工具。请指出这个想法最可能失败的三个原因，按可能性排序。不要给我鼓励。

**二、要求它先做否定再做肯定。**

> 先用 200 字论证为什么这个产品不该做，再用 200 字论证为什么该做。两边都要具体，不要说"取决于执行"。

**三、把判断题改成信息题。**

不问"这个想法好不好"，而问：

> 目前市面上已经有哪些做读书笔记整理的工具？它们各自的定价是多少？用户在评论区最常抱怨什么？

后者拿到的是可以核实的事实，前者拿到的是一段情绪。**永远优先问能被核实的东西。**

### 从想法到方案：五个必须回答的问题

在动手之前，把这五个问题的答案写下来。写不出来的，就是你还没想清楚的地方。

**问题一：谁在什么场景下会用它？**

不合格的答案："喜欢读书的人。"
合格的答案："每周读 1-2 本非虚构书、有做笔记习惯、但笔记散落在 Kindle 标注和微信收藏里、每隔几个月想回顾时找不到的人。"

区别在于：后者你能想象出这个人某天下午具体在干什么。想象不出来，说明你的用户是虚构的。

**问题二：他们现在怎么解决这个问题？**

注意，答案不可能是"没有解决办法"。人们总有办法——可能是用 Notion 手动整理、可能是干脆不回顾了。你的竞品不只是同类产品，还包括**"忍着"和"不做了"**。

如果现有的办法是"忍着"，你要问：忍了这么多年都没崩溃，说明这个痛点有多痛？

**问题三：他们为什么会切换？**

切换是有成本的：学习新工具、迁移旧数据、改变习惯。你的产品要好到能覆盖这个成本。"好一点点"通常不够。

**问题四：为什么是现在？**

这个问题筛掉了大量"其实五年前就能做但没人做成"的想法。如果答案是"因为 LLM 便宜了"，那要具体：便宜到什么程度让这件事从不可行变可行了？

**问题五：最坏情况下我损失什么？**

三个月时间 + 多少钱？这个数字要写出来。写出来之后你会更容易做一件正确的事：**给自己设一个止损点**。

### 用 AI 做竞品扫描：要事实不要总结

竞品调研最容易犯的错是让 AI 直接总结"市面上有哪些竞品"——它会给你一份可能包含已倒闭产品、过时定价、甚至编造名字的清单。

正确的用法是把它当**搜索的加速器**而不是**答案的来源**：

```text
第一步（让 AI 帮你想搜什么）：
"我要做 X。列出 15 个我应该搜索的关键词，
 包括用户可能用来描述这个痛点的口语表达。"

第二步（你自己去搜，或用带联网能力的工具）：
拿着关键词去搜，收集真实的产品页面。

第三步（让 AI 帮你结构化）：
把你收集到的真实页面内容贴给它：
"根据以下 6 个产品的官网内容，做一张对比表，
 列出：定价、目标用户、核心功能、明确说了不做什么。
 如果某项信息在给定内容里没有，写'未提及'，不要推测。"
```

关键是第三步的最后一句。**不加这句话，模型会用训练数据里的印象补全空缺，而你分不出哪些是它读到的、哪些是它编的。**

### 可行性预研：先证伪最脆弱的假设

一个产品方案通常建立在几个假设上。正确的做法不是从最容易的部分开始做，是**从最可能崩掉的假设开始验证**。

以"AI 整理读书笔记"为例，假设可能是：

1. 用户愿意把笔记导入第三方工具（隐私/麻烦）
2. LLM 能从零散标注里提炼出用户认可的结构
3. 成本能压到订阅价之下
4. 用户愿意为此每月付钱

哪个最脆弱？多半是 1 和 4——它们是行为假设，不是技术假设。而工程师的本能会先去验证 2 和 3，因为那是我们熟悉的部分。

**这就是独立开发失败最常见的路径：花三个月完美地解决了技术假设，然后发现行为假设不成立。**

用 AI 做技术假设的快速验证是很划算的：

```text
"我要验证 LLM 能不能从零散的 Kindle 标注里提炼出章节级摘要。
 给我一个 30 行以内的最小验证脚本，
 用 3 条真实风格的标注作为输入，
 让我能在 10 分钟内判断效果够不够好。"
```

注意"30 行以内""10 分钟内判断"这两个约束。**预研的目的是尽快拿到"行/不行"的结论，不是写出可复用的代码。**

### 一份能开工的方案长什么样

跑完上面的流程，你应该能写出一页纸，包含：

```markdown
## 一句话描述
给谁、解决什么问题、和现在的做法比好在哪。

## 用户与场景
一个具体的人，一个具体的下午。

## 最小可收费切面
砍到不能再砍的功能集合（M18 会展开）。

## 技术方案
选型 + 已验证的关键假设 + 未验证的风险点。

## 成本估算
每用户每月的推理成本量级（不要精确，要量级）。

## 止损点
做到什么程度、花了多久还没有 X 个付费用户，就停。
```

这一页纸的价值不在于它有多准——它一定会变。价值在于**它把你的假设显式化了**，三个月后你能回来看是哪个假设错了，而不是笼统地觉得"这事没做成"。

### 一个必须警惕的陷阱：AI 让做方案变得太舒服

和 AI 讨论方案有一种奇特的爽感：思路越聊越清晰、文档越写越漂亮、每个问题都有答案。这种爽感会让人**在方案阶段停留过久**。

方案写到第五版还在改的时候，你要问自己一句：**我现在缺的是想得更清楚，还是缺一个真实用户的反馈？**

九成情况下是后者。方案的边际收益衰减得非常快，而真实反馈的信息量是方案推演给不了的。**写到"够开工"就停手，剩下的问题让现实来回答。**

### 动手 5 分钟

拿你手上最想做的那个想法，做一次"反向论证"。

1. 让 AI 扮演一个投资过很多失败工具类产品的人，指出这个想法最可能失败的三个原因，明确要求不给鼓励。
2. 对每个原因，写下你的真实回应——是"这个我有办法"还是"这个我确实没想过"。
3. 挑出你的假设里最脆弱的那一个（多半是行为假设不是技术假设），设计一个 1 小时内能做完的验证动作。

**验收标准**：那三个失败原因里，至少有一个是你之前没认真想过的。如果三个你都早想过并且都有答案，说明你的提问还是太温和了——再逼一轮。

### 用市场数据做验证：一个最小竞品探测器

竞品调研最怕 AI 编造信息。这里给一个"用真实数据验证假设"的最小脚本——不依赖 AI，直接抓公开数据做决策参考：

```python
"""scripts/competitor_snapshot.py —— 竞品公开数据快照，辅助可行性判断"""
import json
import time
from urllib.request import Request, urlopen
from pathlib import Path

# 目标竞品主页（你手动确定的真实 URL，不是 AI 生成的）
COMPETITORS = [
    {"name": "Readwise", "url": "https://readwise.io"},
    {"name": "Notion", "url": "https://notion.so"},
    # 这里填你真实查到的竞品 URL
]

def check_site(name: str, url: str) -> dict:
    """检查一个竞品站点是否存活、返回什么状态码。"""
    try:
        req = Request(url, headers={"User-Agent": "Mozilla/5.0"})
        resp = urlopen(req, timeout=10)
        return {"name": name, "url": url, "status": resp.status, "alive": True}
    except Exception as e:
        return {"name": name, "url": url, "status": 0, "alive": False, "error": str(e)}

def main():
    results = [check_site(c["name"], c["url"]) for c in COMPETITORS]

    alive = [r for r in results if r["alive"]]
    dead = [r for r in results if not r["alive"]]

    print(f"竞品快照 ({time.strftime('%Y-%m-%d')}):")
    print(f"  存活: {len(alive)}/{len(results)}")
    print(f"  未响应: {len(dead)}/{len(results)}")

    for r in dead:
        print(f"  ⚠ {r['name']} ({r['url']}): {r.get('error', 'unknown')}")

    # 保存快照，三个月后可以对比看哪些竞品倒了（市场变化信号）
    snapshot_path = Path("docs/competitor_snapshot.json")
    snapshot_path.parent.mkdir(exist_ok=True)
    snapshot_path.write_text(json.dumps(results, indent=2, ensure_ascii=False))

if __name__ == "__main__":
    main()
```

这个脚本的价值不是"自动化"——跑一次只要 5 秒。价值在于**它只记录可核实的事实**（站点是否存活、返回什么状态码），不包含任何推测。三个月后回来看这张快照，你能看到客观的市场变化，而不是自己脑补的"我觉得他们做得不好"。

### 要点总结

- **"你觉得怎么样"是征求认可的问题，模型会附和。** 换成征求反对（指定挑刺角色）、先否后肯、或者把判断题改成可核实的信息题。
- 动手前必须回答五个问题：谁在什么场景用、他们现在怎么解决、为什么会切换、为什么是现在、最坏损失多少。答不出的就是没想清楚的。
- **你的竞品包括"忍着"和"不做了"。** 如果用户忍了很多年都没崩溃，先掂量这个痛点到底有多痛。
- 竞品调研让 AI 当搜索加速器，不当答案来源。贴真实内容给它做结构化，并明确要求"没有的信息写'未提及'，不要推测"。
- **先证伪最脆弱的假设，而不是先做最熟悉的部分。** 工程师的本能是先验证技术假设，但崩掉的通常是行为假设。
- 预研脚本要有"30 行以内、10 分钟出结论"这类约束——目的是拿结论，不是写可复用代码。
- 方案的边际收益衰减很快。**写到"够开工"就停手**，剩下的交给真实用户回答。
