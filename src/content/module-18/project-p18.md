## P18：给你的产品装上收款闭环与单位经济仪表盘

> 本项目涉及支付与用户数据，请全程在测试环境完成。涉及真实收款、税务登记与合规条款的决定，请咨询相应资质的专业人士。本项目内容不构成法律、税务或投资建议。

P17 交付了一个能用的应用。P18 让它变成一门**能算清账的生意**。

这个项目的核心不是「接通支付」—— 那只是其中一环。核心是建立一张能实时回答**「这个用户这个月让我赚了还是亏了」**的仪表盘。没有这张表，你的所有增长决策都是在赌博。

### 项目目标

在 P17 的应用上补齐商业闭环：

- 用 L18-01/02 的方法确定定价与最小可收费范围
- 用 L18-03 的模型设计订阅档位与免费额度（含成本上限）
- 用 L18-04 的状态机与幂等实现账号、订阅、支付、退款
- 用 L18-05 的模型建立单位经济仪表盘与成本告警
- 用 L18-06 的清单完成合规最小集

规模控制：**订阅档位不超过两档，先做单次付费或月付，不做年付**。年付涉及按比例退款和更长的对账周期，早期不值得。

### 验收标准

- [ ] 定价方案文档：档位、额度、超额行为、定价依据（对标了什么）
- [ ] 完整支付闭环：注册 → 订阅 → 使用 → 续费 → 取消 → 退款（测试环境跑通）
- [ ] 订阅状态机代码，含 `PAST_DUE` 宽限期
- [ ] 权限与额度映射集中在一处，覆盖全部状态
- [ ] Webhook 验签 + 幂等（数据库唯一约束实现）
- [ ] Webhook 重放三次，数据不变（附验证记录）
- [ ] 对账脚本，跑通并输出差异报告
- [ ] 单位经济仪表盘：中位数 / P95 / 最坏单次成本 + 混合毛利率
- [ ] 每日成本告警脚本（单用户超阈值告警）
- [ ] 免费额度成本上限的计算过程与超出后的预案
- [ ] 滥用防护三层（邮箱域名、双维度计额、行为检测）
- [ ] 合规清单十一条 + 隐私声明草稿
- [ ] `delete_user` 脚本，dry_run 验证覆盖全部数据位置

### 分阶段实施

**第一阶段：定价设计（约 1 小时）**

先算再定。顺序不能反 —— 很多人先拍一个价格再去算成本，算出来亏了又不好意思涨。

```markdown
# 定价方案

## 成本基线
- 单次调用最坏成本：$____（最长上下文 + 最贵路径）
- 单次调用中位成本：$____
- 每用户固定分摊：$____/月

## 档位
| 档位 | 月费 | 含额度 | 超额行为 | 超额单价 | 单价/成本倍数 |
|------|------|--------|---------|---------|--------------|
| 免费 |  $0  |        | 硬停    |    —    |      —       |
| 基础 |      |        | 硬停    |         |     ≥3       |
| 专业 |      |        | 软超    |         |     ≥3       |

## 定价依据
- 用户现在为这件事花多少钱/时间：
- 替代方案的价格：
- 我取了价值的百分之几：

## 免费层成本上限
- 免费额度 × 单次成本 × 预期免费用户数 = $____/月
- 超过 ____ 个免费用户后，我打算：
```

「单价/成本倍数 ≥3」那一列是硬约束，不满足就回去改数字。

**第二阶段：账号与订阅状态机（约 1.5 小时）**

先写状态机和权限映射，再接支付。顺序很重要 —— 状态机是你自己的领域模型，支付网关只是它的一个数据来源。反过来做（照着网关的字段设计自己的模型），换网关时要重写。

这部分属于 L17-01 定义的红线代码，**自己写，不要全权交给 AI**。可以让它写测试和样板。

必须有的测试：

```python
def test_illegal_transition_rejected():
    with pytest.raises(ValueError):
        transition(SubStatus.EXPIRED, SubStatus.ACTIVE)  # 不能跳过支付

def test_past_due_keeps_features():
    """续费失败宽限期内不能降级 —— 这是最容易写错的一条。"""
    assert FEATURES[SubStatus.PAST_DUE] == FEATURES[SubStatus.ACTIVE]

def test_every_status_has_mapping():
    """新增状态时必须补映射。"""
    for s in SubStatus:
        assert s in FEATURES and s in QUOTA
```

**第三阶段：支付与 Webhook（约 1.5 小时）**

接通网关，重点在幂等和验签。

验证方式不是「点一次付款成功了」，而是把这五条路径各跑一遍：

```
1. 付款成功 → 用户变 ACTIVE，额度到账
2. 付款失败 → 用户停留在 NONE，没有被误开通
3. 付款成功但 webhook 重放 3 次 → 状态和额度不变
4. 续费失败 → 用户变 PAST_DUE，功能不降级，收到提醒
5. 退款 → 用户变 REFUNDED，额度清零
```

第 3 条用网关控制台的「重发事件」功能做。这是整个项目里最容易糊弄过去、也最容易在生产上出事的一条。

**第四阶段：单位经济仪表盘（约 1 小时）**

先埋数据，再做展示。每次调用都要记：

```sql
CREATE TABLE api_calls (
  id          bigserial PRIMARY KEY,
  user_id     text NOT NULL,
  model       text NOT NULL,
  in_tokens   int  NOT NULL,
  out_tokens  int  NOT NULL,
  cost_usd    numeric(10,6) NOT NULL,
  success     boolean NOT NULL,      -- 失败也要记，成本已经产生
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON api_calls (user_id, created_at);
```

`success` 字段容易被忘。失败的调用不扣用户额度，但成本已经花了 —— 不记就会低估成本。

仪表盘至少要回答四个问题：

1. 本月每用户成本的中位数 / P95 / 最大值
2. 本月混合毛利率（按 L18-05 的模型）
3. 免费用户当月总成本，距离上限还有多少
4. 单日成本 Top 10 的账号

第 4 条是异常发现的主要途径，比看总量有用得多。

**第五阶段：合规最小集（约 0.5 小时）**

走一遍 L18-06 的十一条清单。重点做两件事：写 `delete_user(dry_run=True)` 并跑一次看数据散落在几处；翻十条日志确认没有明文内容和身份信息。

### 常见翻车点

**先接支付再设计状态机。** 结果是你的领域模型长得和某个网关一模一样，换网关等于重写。

**幂等靠先查后写。** `if not exists: insert` 在 webhook 并发重试下会双双通过，用户被开通两次。必须用数据库唯一约束。

**忘了 `PAST_DUE`。** 续费失败立刻停服，把本来愿意付钱的用户赶走了。这是真实世界里损失最大的一个疏漏。

**成本记录漏了失败调用。** 于是你的成本模型系统性偏低，越增长偏差越大。

**免费层没有盖子。** 上线当天被人发现，一晚上跑出四位数账单。

**隐私政策抄了一份跟产品对不上的。** 写了「我们不会将数据发送给第三方」，而你的产品每次调用都在发给模型厂商 —— 这是虚假陈述，比不写危险。

**只在自己的账号上测过。** 用两个账号交叉测一次，特别是额度和权限 —— 「A 用完额度导致 B 也被限制」这类 bug 只有多账号才测得出来。

### 自检问题

- 再来 100 个用户，我这个月多赚还是多亏多少钱？（说出具体数字）
- 让毛利率翻负的临界条件是什么？
- 明天来了 1000 个免费用户，我会多花多少钱？有上限吗？
- 一个 webhook 被重放 10 次，会发生什么？
- 有用户要求删除全部数据，我需要执行几个操作？多久？
- 我的隐私政策里有没有一条是产品实际做不到的？

最后一条要逐句核对。写了做不到，比没写更危险。

### 可选：用 AI Skills 辅助产品化决策记录

P18 涉及大量需要权衡的决策：定价档位、免费额度上限、合规风险评估、成本告警阈值。这些决策的"为什么"比"是什么"更重要——三个月后你回头看自己的定价，如果不记得当时怎么想的，就很难判断该不该调。

建议用 OpenSpec + Superpowers 工作流（L17-13）记录关键决策过程：

```text
# 在 P18 项目中用 AI Skills 做决策记录

## 定价决策
用 brainstorming skill 发散定价方案：
  → 至少列出 3 种不同的档位组合
  → 对每种方案跑 L18-03 的单位经济模型
  → 输出：选定的定价方案 + 被否决的方案及否决理由

## 免费额度决策
用 writing-plans skill 做免费层成本推演：
  → 输入：单次调用成本、预期免费用户数、月预算上限
  → 输出：不同免费额度下的月度成本曲线
  → 记录：你选的免费额度 + 触发上限后的预案

## 合规决策
用 systematic-debugging skill 逐条过 L18-06 合规清单：
  → 逐条标注：已满足 / 不适用 / 需补充什么
  → 隐私政策逐句核对结果
  → 记录：合规缺口 + 优先级排序
```

这些决策记录放在 `docs/decisions/` 目录下，每条决策一个文件，格式参考 L14-01 的 ADR 模板。不必写完整的 ADR——一页纸说清"背景、决策、备选方案、后果"即可。

**为什么做这件事**：P18 的决策直接影响你的收入和法律责任。P17 的返工点记录（project-p17.md）让你下次写代码更快，P18 的决策记录让你下次做商业化决策更准——两者都是复利资产。

### 要点总结

- 项目核心不是「接通支付」，是建立能回答「**这个用户这个月让我赚了还是亏了**」的仪表盘。
- **先算成本再定价**，顺序反了就会不好意思涨价；「超额单价 ≥ 3 倍成本」是硬约束。
- **先写状态机再接支付**：状态机是你的领域模型，网关只是它的数据来源；照着网关字段设计模型，换网关等于重写。
- 支付验证不是「付款成功了」，是**五条路径各跑一遍**，其中 **webhook 重放三次**最关键也最常被糊弄。
- **幂等必须靠数据库唯一约束**，先查后写在并发下会双双通过。
- 成本记录**必须包含失败调用** —— 不扣用户额度但成本已产生，漏记会让模型系统性偏低。
- 仪表盘的第四问「**单日成本 Top 10 账号**」是异常发现的主要途径，比看总量有用。
- 隐私政策要**逐句核对产品实际行为**；写了做不到是虚假陈述，比不写更危险。
