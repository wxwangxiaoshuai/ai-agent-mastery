## 合规与风险：条款、隐私与内容责任

> 重要说明：本节是工程视角的风险清单，**不构成法律意见**。不同国家和地区的法律差异很大，且在持续变化。涉及具体条款、跨境数据、税务和责任划分的决定，请咨询有相应执业资质的专业人士。本节的目标是让你知道**哪些地方需要问专业人士**，而不是让你自己拍板。

工程师做产品最容易忽略的就是这一块，理由通常是「我还这么小，没人管我」。这个判断在很多时候是对的，但它有两个漏洞：**风险不是按你的规模来的，是按你碰了什么数据、做出了什么承诺来的**；而且合规问题往往在你最不能承受打击的时候（第一个大客户、第一次被媒体提到）暴露出来。

好消息是，早期需要做的事情比想象中少，而且大部分是一次性的。

### 三个必须搞清楚的角色关系

先把关系理顺，很多困惑来自这里没搞清。

**你和用户之间。** 你收集了他的什么数据、用来做什么、存多久、他能不能要求删除。这是隐私政策要说明的内容。

**你和模型厂商之间。** 用户的数据经过你传给了模型厂商 —— 这件事用户知道吗？厂商会用这些数据做训练吗？（多数厂商的 API 层默认不用于训练，但你需要确认并写清楚，而且这个策略可能变化。）这是**最容易被漏掉的一环**：用户以为数据只给了你。

**你和内容之间。** 用户用你的产品生成了内容，出了问题谁负责。AI 生成的内容可能不准确、可能侵权、可能违规。你的服务条款需要对此有明确表述。

这三条关系里，第二条是 AI 产品特有的，也是最需要主动披露的。

### 数据最小化：最便宜的合规策略

绝大多数合规风险来自「你存了不该存的数据」。所以最有效的策略不是把合规做得多完善，是**一开始就少存**。

三个可以立刻执行的原则：

**一、能不存就不存。** 用户上传的文档处理完就删，不留副本。很多产品默认保存所有历史，但如果你的产品不需要历史功能（L18-02 建议早期砍掉），那就不要存 —— 存了就要负责。

**二、能不收就不收。** 注册只要邮箱，不要手机号、不要真实姓名、不要生日。每多一个字段就多一份责任，而这些字段在早期几乎没用。

**三、能匿名就匿名。** 日志和分析数据用哈希后的 ID，不要直接记邮箱和原始内容。

```python
# 日志里不要出现原始内容和身份信息
def log_call(user_id: str, prompt: str, result: str, cost: float):
    logger.info(
        'call user=%s in_len=%d out_len=%d cost=%.4f in_hash=%s',
        hashlib.sha256(user_id.encode()).hexdigest()[:12],  # 假名化
        len(prompt), len(result), cost,
        hashlib.sha256(prompt.encode()).hexdigest()[:12],   # 用于查重不用于还原
    )
```

用哈希前缀做用户标识，你依然能做用量统计和异常排查，但日志泄漏时不会直接暴露身份。这个改动成本极低，价值很高。

**保留期限也要写死并自动执行**：

```python
async def purge_expired():
    """每日跑：按保留策略删除过期数据。"""
    await db.execute("DELETE FROM uploads WHERE created_at < now() - interval '7 days'")
    await db.execute("DELETE FROM api_calls WHERE created_at < now() - interval '90 days'")
    await db.execute("DELETE FROM sessions WHERE expires_at < now()")
```

有这个脚本，你的隐私政策里「我们保留 X 天」才不是一句空话。

### 删除路径必须真的能走通

「用户可以要求删除数据」这句话写进政策很容易，真要执行时才发现数据散落在七八个地方：主库、缓存、日志、备份、分析平台、邮件服务商、支付网关。

早期就把删除做成一个**能一键跑通的脚本**，比事后手工找便宜得多：

```python
async def delete_user(user_id: str, *, dry_run: bool = True) -> dict[str, int]:
    """删除用户全部数据。先 dry_run 看影响面，确认后再执行。"""
    targets = [
        ('uploads',   'uploads',   'user_id'),
        ('api_calls', 'api_calls', 'user_id'),
        ('sessions',  'sessions',  'user_id'),
        ('users',     'users',     'id'),
    ]
    report = {}
    for name, table, col in targets:
        report[name] = await db.fetchval(
            f'SELECT count(*) FROM {table} WHERE {col}=$1', user_id)
        if not dry_run:
            await db.execute(f'DELETE FROM {table} WHERE {col}=$1', user_id)

    if not dry_run:
        await cache.delete_prefix(f'user:{user_id}:')
        await storage.delete_prefix(f'uploads/{user_id}/')
        await email_provider.delete_contact(user_id)
        # 备份里的数据随保留期自然过期 —— 这一点要写进隐私政策
    return report
```

最后那行注释很关键：**备份里的数据通常无法即时删除**，这是所有人都面临的现实问题。诚实的做法是在隐私政策里说明「备份中的数据将在 X 天保留期后自动失效」，而不是假装它不存在。

支付记录通常有法定的保存义务，不能因为用户要求删除就删 —— 这类例外也要在政策里写清楚。具体保存年限各地不同，属于要问专业人士的事项。

### 你必须披露的几件事

不需要一份三十页的法律文件，但有几件事必须让用户知道。用大白话写在一个页面上就行：

```markdown
## 关于你的数据（写给用户看的大白话版）

**我们收集什么**
- 你的邮箱（用于登录和通知）
- 你上传的内容（用于生成结果）
- 使用记录（调用次数、时间，用于计费和排障）

**内容会去哪**
你上传的内容会发送给第三方大模型服务商用于生成结果。
我们使用的服务商是 <名称>，其 API 数据处理政策见 <链接>。
我们自己不会用你的内容训练任何模型。

**保留多久**
- 上传的原始内容：7 天后自动删除
- 生成结果：你删除即删除
- 使用记录（不含内容）：90 天

**你可以做什么**
- 随时导出你的数据
- 随时要求删除账号和全部数据（<邮箱>，我们会在 7 天内处理）
- 备份中的数据将在 30 天保留期后自动失效

**AI 生成内容的说明**
生成结果可能包含错误或不准确的信息，请在使用前自行核实。
你需要对如何使用这些内容负责。
```

最后一段（AI 生成内容的免责说明）是 AI 产品必须有的。它不能让你完全免责，但清晰的预期管理能避免绝大多数争议。

写这份东西的时候，**别用 AI 直接生成一份法律文件然后原样贴上去**。可以用它起草结构，但每一条你都要确认和你的产品实际行为一致 —— 写了做不到，比不写更糟糕，因为那变成了虚假陈述。

### 内容责任与滥用防护

如果你的产品能生成开放内容，你需要考虑有人拿它做坏事。

早期的最小防护：

**一、输入侧过滤。** 明显违规的请求直接拒绝。不需要多复杂，模型厂商通常提供审核接口，接上即可。

**二、留下审计线索。** 记录调用的时间、账号、输入哈希（不是原文）。出事时你需要能配合调查，同时又不至于自己存了一堆敏感原文。

**三、服务条款里写明禁止用途。** 并保留封禁账号的权利。这一条在你需要封人时会很有用。

**四、举报入口。** 一个邮箱地址就够。

M13 讲的护栏和 M9 讲的沙箱是这部分的技术基础，这里只强调**流程上要有一条从举报到处理的路径**，哪怕这条路径就是「用户发邮件给我，我手工看」。

### 什么时候必须找专业人士

这是本节最重要的部分。以下情况不要自己判断：

- 你的用户涉及**未成年人**
- 你处理**健康、金融、生物识别**等敏感类别数据
- 你的用户在**欧盟、英国**等有严格数据法规的地区，或者你面向全球
- 你要和**企业客户签合同**（数据处理协议、SLA、责任上限条款）
- 涉及**跨境数据传输**
- 你的产品输出会被用于**可能影响他人权益的决策**（招聘、信贷、医疗、法律）
- 涉及**税务登记、发票、跨境收款**
- 你收到了**律师函或监管问询**

前期咨询一次的成本，通常远低于事后处理的成本。而且这类咨询往往是一次性的 —— 把结构定对，后面照着执行就行。

一个务实的建议：**在有第一个企业客户之前，先把面向个人用户的最小版本做扎实**（隐私政策、删除路径、免责说明）。企业客户会带来完全不同层级的合规要求，那时候再投入是合理的顺序。

### 一份早期检查清单

```markdown
- [ ] 有隐私政策页面，且内容与产品实际行为一致
- [ ] 有服务条款，含 AI 生成内容的免责说明和禁止用途
- [ ] 明确披露了「内容会发给第三方模型服务商」
- [ ] 数据保留期限写死并有自动清理脚本
- [ ] 删除用户数据的脚本存在且跑通过（dry_run 验证过）
- [ ] 日志中不含原始内容和明文身份信息
- [ ] 注册只收必要字段
- [ ] 有举报/联系邮箱
- [ ] 秘钥不在代码库里（L17-08 的 gitleaks）
- [ ] 备份加密，且演练过恢复
- [ ] 知道自己属不属于「必须找专业人士」的那几种情况
```

十一条，一天之内能做完大部分。这是一人公司在合规上能达到的一个合理起点。

### 动手 5 分钟

给你的产品做一次数据盘点。

1. 列出你实际存储的所有用户数据字段，逐个问「这个字段不存，产品还能用吗」，标出可以删掉的。
2. 写一个 `delete_user(dry_run=True)`，跑一次，看看用户数据到底散落在几个地方 —— 通常比你以为的多。
3. 检查你的日志：随便翻十条，看有没有出现明文邮箱、原始输入内容或 API key。

**验收标准**：你能列出用户数据存在的全部位置（包括缓存、对象存储、第三方服务），并且删除脚本覆盖了其中每一个。如果日志里翻出了明文内容，这是当天就该修的 —— 日志通常是最容易泄漏的一环。

### 要点总结

- 本节是工程视角的风险清单，**不构成法律意见**；目标是让你知道**哪些地方需要问专业人士**。
- 风险不按你的规模来，**按你碰了什么数据、做了什么承诺来**；且往往在最不能承受打击时暴露。
- 三个角色关系里，**「用户数据经你传给了模型厂商」是 AI 产品特有且最容易漏掉的披露项**。
- 最便宜的合规策略是**数据最小化**：能不存就不存、能不收就不收、能匿名就匿名（日志用哈希前缀，成本极低）。
- **保留期限要写死并有自动清理脚本**，否则政策里的「保留 X 天」只是空话。
- **删除路径要做成能一键跑通的脚本**；备份中的数据无法即时删除，诚实写进政策而不是假装不存在。
- 披露文件**别让 AI 直接生成后原样贴上** —— 写了做不到比不写更糟，那是虚假陈述。
- 涉及**未成年人、敏感数据、严格法规地区、企业合同、跨境、影响他人权益的决策、税务**时，必须找专业人士，不要自己拍板。
